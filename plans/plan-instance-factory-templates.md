# `instanceFactory` Strategy with Templated Block Classes

**Status:** Superseded / revised by T9
[`plan-block-registration.md`](./plan-block-registration.md). The
original Pattern A conclusion that the existing `variant` key was
sufficient is no longer correct for multi-Config-per-block projects.
The selected T9 design extends the factory key to `(blockType,
variant, configTag)` and emits registration lambdas from per-block
trampolines.
**Cross-references:** [`plan-ip-namespaces-and-parameterization.md`](./plan-ip-namespaces-and-parameterization.md) §11 #6, [`plan-parameterizable-config-template.md`](./plan-parameterizable-config-template.md) "Further considerations" #3, [`plan-block-registration.md`](./plan-block-registration.md). Existing factory: [`common/systemc/instanceFactory.h`](./common/systemc/instanceFactory.h), [`common/systemc/instanceFactory.cpp`](./common/systemc/instanceFactory.cpp).

## What the existing factory does

The factory is a **string-keyed** registry of `std::function`s that produce `std::shared_ptr<blockBase>`:

```cpp
typedef std::function< std::shared_ptr< blockBase >(const char * blockName,
                                                    const char * variant,
                                                    blockBaseMode bbMode) > blockFactoryFunctionType;
static void registerBlock(std::string blockType, blockFactoryFunctionType);
static void registerBlock(std::string blockType, blockFactoryFunctionType, std::string variant);
// T9 adds:
static void registerBlock(std::string blockType, blockFactoryFunctionType, std::string variant, std::string configTag);
```

Generated block classes register themselves at static-init time via a per-class `registerBlock` struct (see `model/debayer.h`, `model/preprocess.h`, etc.):

```cpp
// generated in model/<block>.h
struct registerBlock {
    registerBlock() {
        instanceFactory::registerBlock("debayer_model",
            [](const char* blockName, const char* variant, blockBaseMode bbMode) {
                return std::make_shared<debayer>(blockName, variant, bbMode);
            }, "");
    }
};
static registerBlock registerBlock_;   // static-init drops the entry into the map
```

Lookup happens via `createInstance(hierarchy, blockName, blockTypeUser, …)` which composes the effective block type and checks the variant-specific entry before the variant-less entry. Under T9, this fallback is scoped to the same `configTag`: lookup first checks `(blockType, variant, configTag)`, then `(blockType, "", configTag)`, then errors. There is no fallback across Config tags.

## What changes when blocks become `template<typename Config>`

Once `class debayer` becomes `template<typename Config> class debayer { … };`:

- `std::make_shared<debayer>(…)` no longer compiles — the consumer must pick a Config: `std::make_shared<debayer<config_8bpc>>(…)`.
- Two instances at different bitwidths in one binary are **two distinct C++ types** that both satisfy `blockBase`. Both must be reachable from the factory.
- The factory's *return* type does not change: `blockBase` is non-template (it is the polymorphic glue that lets `simController` walk the model). Each `debayer<C>` derives from `blockBase` via `debayerBase<C>` → `blockBase` (the existing pattern, just with `<C>` plumbed through `*Base`).

The factory itself does not need to become a template. What changes is *what gets registered*.

## Candidate registration patterns

### Pattern A — One `registerBlock` per template instantiation, generated per `(block, variant, Config, configTag)` tuple

```cpp
// generated by arch2code in a per-block trampoline TU
namespace {
    struct register_debayer_config_8bpc {
        register_debayer_config_8bpc() {
            instanceFactory::registerBlock(
                "debayer_model",  // same string key as today
                [](const char* blockName, const char* variant, blockBaseMode bbMode) {
                    return std::make_shared<debayer<config_8bpc>>(blockName, variant, bbMode);
                },
                "variant0",
                "config_8bpc"     // stable configTag disambiguates C++ type
            );
        }
    } register_debayer_config_8bpc_;

    struct register_debayer_config_12bpc { … };
}
```

- The factory's existing `(blockType, variant)` key is **not** enough when two Configs use the same variant name in one project. T9 adds `configTag` so each concrete `debayer<Config>` registers under a distinct key.
- The IP's own header still declares the `template<typename Config> class debayer { … };`. The IP does **not** know which Configs the consumer will instantiate; that's a consuming-project property.
- arch2code emits a trampoline TU per parameterized block per project. The trampoline emits one lambda per unique `(block, variant, Config, configTag)` tuple and owns the static-init object.

**Pros:**
- Preserves the non-template factory return type and existing overloads.
- Supports multiple Configs for the same `(blockType, variant)`.
- Symmetric with existing `variant` plumbing (`createInstance(hierarchy, blockName, blockType, variant)` already takes a variant string).
- No new compile-time machinery; each registration TU has trivial complexity.

**Cons:**
- Requires a factory key extension and generated `configTag` plumbing.
- Each consuming project must list its `(IP, variant, Config)` pairs in its YAML so arch2code can emit the registrations. (Acceptable — this list already exists conceptually as the instance tree plus Config bindings.)
- Two consuming projects that both want the same `(IP, Config)` pair still each emit their own TU. Fine; not duplicated within a single binary.

### Pattern B — Generic `register<T>(...)` template wrapper added to the factory

Add to `instanceFactory`:

```cpp
template<typename Block>
static void registerBlock(std::string blockType, std::string variant, std::string configTag) {
    registerBlock(blockType,
        [](const char* n, const char* v, blockBaseMode m) {
            return std::make_shared<Block>(n, v, m);
        },
        variant,
        configTag);
}
```

The generated registration becomes:

```cpp
struct register_debayer_config_8bpc {
    register_debayer_config_8bpc() {
        instanceFactory::registerBlock<debayer<config_8bpc>>(
            "debayer_model", "variant0", "config_8bpc");
    }
} register_debayer_config_8bpc_;
```

**Pros:** very slightly less generated boilerplate.

**Cons:**
- Adds a template helper to the factory header; every consumer of the factory header now sees an extra template. Marginal compile-time cost.
- No real expressiveness gain over Pattern A.

### Pattern C — Make `instanceFactory` itself templated

Discarded. The factory's whole purpose is to provide a non-template polymorphic entry point so `simController` doesn't have to know about Configs. Templatising it would just push the Config knowledge into every caller.

## Decision

**Revised Pattern A with `configTag`.** Keep `instanceFactory`
non-templated, but extend the registration key from `(blockType,
variant)` to `(blockType, variant, configTag)`. Existing overloads
forward to a reserved stable-string sentinel
`instanceFactory::noConfigTag` for non-templated callers.

Pattern B is acceptable as a **later optimization** (purely a
generated-code-volume reduction), but it does not remove the need for
the `configTag` key.

### Why the existing variant string is not enough

Today the variant string is consumer-supplied free text (the `--variant=…` style options). It can distinguish named parameter variants, but it cannot distinguish two Config policy types bound to the same named variant in one project. With only `(blockType, variant)`, first-write-wins registration silently keeps whichever Config registered first.

T9 keeps variant fallback but scopes it to the same Config tag. This preserves existing behavior for non-templated callers while preventing a missing `ipFastConfig` variant from falling back to an `ipDefaultConfig` entry.

## Generated example

Given `ipInstances:` in the consuming project's YAML:

```yaml
ipInstances:
  - name: u_interp_hd
    block: debayer
    variant: 8bpc
    config: config_8bpc
  - name: u_interp_uhd
    block: debayer
    variant: 12bpc
    config: config_12bpc
```

arch2code emits one registration TU per *unique* `(block, config)` pair (not per instance — multiple instances at the same Config share one registration):

```cpp
// generated: model/debayer_register_config_8bpc.cpp
#include "debayer.h"
#include "debayer_configs.h"
#include "instanceFactory.h"

namespace {
struct reg_debayer_config_8bpc {
    reg_debayer_config_8bpc() {
        instanceFactory::registerBlock(
            "debayer_model",
            [](const char* blockName, const char* variant, blockBaseMode bbMode) {
                return std::make_shared<debayer<config_8bpc>>(blockName, variant, bbMode);
            },
            "variant0",
            "config_8bpc");
    }
} reg_debayer_config_8bpc_;
} // namespace
```

Plus generated `createInstance(..., variant, configTag)` calls at construction sites. Non-templated callers keep using existing overloads, which forward to `instanceFactory::noConfigTag`.

## Boundary: arch2code vs. consuming project

| Artifact | Generated by | Lives in |
|----------|-------------|----------|
| `template<typename Config> class debayer` | arch2code from IP YAML | IP repo (`<ip>/model/`) |
| Concrete `debayer<config_8bpc>` lambda instantiation | arch2code from consuming-project Config binding | Trampoline TU |
| `reg_debayer_project.cpp` trampoline TU | arch2code from **consuming-project** YAML / instance tree Config bindings | Consuming project build artifact |
| `config_8bpc` struct | arch2code from consuming-project YAML | Consuming project |

The IP cannot know which Configs the consumer will use; the consumer cannot know how the block is implemented. The split keeps these orthogonal.

## Prototype validation

The revised T9 mechanics are prototyped before generator changes:

- `make -C ../../proto/model step6`

That prototype validates direct trampoline lambdas, stable-string `configTag` keys, multi-Config coexistence for one variant, variant fallback scoped to one Config tag, active force-linking for non-templated self-registration, and trampoline-owned verilated-style wrapper registration.

## Open follow-ups

- **Tandem-mode interaction.** `instanceFactory` currently uses `inst == INSTANCE_FACTORY_DEFAULT` vs. tandem suffix to pick the registration. With templated blocks, the tandem block class is *also* templated (`debayerTandem<Config>`), so the same registration pattern applies — emit entries keyed by `(debayer_tandem, variant, configTag)` etc. The exact tandem-pair record shape remains in T9 Plan-9.
- **`addParam` per (block, variant) for ipParameters.** The factory already has `addParam(name, value)` and `getParam(blockName, variant, param)`. These remain useful as the *runtime* / arch2code-tooling-only path; they do not replace the C++ Config struct (which is compile-time). Generator should populate both: the Config struct for compile-time use, and the addParam map for tooling that introspects values at run time.
