## Plan: Parameterizable Types — Schema, C++ Emission, and Pack/Unpack Stability

Add a new top-level `ipParameters` section to the project YAML whose content is treated as an embedded YAML file — its `constants` and `types` sub-sections are parsed by the normal `processSection` / `processSingleFile` pipeline under a dedicated context, with `isParameterizable=True` and `maxBitwidth` flags automatically set on every entry. Any downstream constant, type, struct, or array size that is derived from (or depends on) a parameterizable entry inherits the flag transitively. Thread this metadata through C++ type selection, pack/unpack generation, and address-space calculation so generated source text never changes when an external parameter value changes, and so address/memory sizing always uses the declared maximum.

### Steps

1. **Add `ipParameters` section to the schema** in [builder/base/config/schema.yaml](builder/base/config/schema.yaml): Add a new top-level `ipParameters` node whose body mirrors the `constants` and `types` schema nodes exactly (same field definitions), plus `maxBitwidth: optional(0)` on the `types` sub-node and `maxValue: optional(0)` on the `constants` sub-node. When `processSingleFile` encounters `ipParameters`, it feeds the inner `constants` and `types` blocks through the existing `processSection` pipeline as if they were a normal included YAML file, but under a dedicated `_ipParameters` context so their origin is always traceable.

2. **Extend the `types` and `constants` nodes in schema** in [builder/base/config/schema.yaml](builder/base/config/schema.yaml): Add `isParameterizable: optional(false)` and `maxBitwidth: optional(0)` directly on the `types` node, and `isParameterizable: optional(false)` and `maxValue: optional(0)` on the `constants` node, following the same pattern as `isSigned: optional(false)` (line 93). These fields are populated automatically when entries are processed via `ipParameters`; they can also be set directly on a type/constant for explicit one-off cases.

3. **Process `ipParameters` as an embedded YAML file** in [builder/base/pysrc/processYaml.py](builder/base/pysrc/processYaml.py): In `processSingleFile`, detect the `ipParameters` section and call `processSection('constants', ...)` and `processSection('types', ...)` on its sub-data under the `_ipParameters` context, then stamp `isParameterizable=True` and the declared `maxValue`/`maxBitwidth` onto the resulting entries in `self.data`. After all YAML files are loaded, run a **transitive propagation pass**: walk `self.data['constants']`, `self.data['types']`, and `self.data['structures']` and mark any entry as parameterizable if its `width`, `value`, `arraySize`, or any constituent field resolves through a constant or type that is already marked parameterizable. Validate that `maxBitwidth` is present for every parameterizable type and that the currently-resolved value does not exceed it — emit a hard generator error (not a warning) if it does.

4. **Propagate `isParameterizable` through type resolution and C++ struct-var decoration** in [builder/base/pysrc/processYaml.py](builder/base/pysrc/processYaml.py) (`getContextData` ~line 866) and [builder/base/pysrc/systemcGen.py](builder/base/pysrc/systemcGen.py) (per-var loop ~lines 128–146): Force `platformDataType` to `uint64_t` when `isParameterizable` is true regardless of `realwidth`; in `systemcGen.py` set `varData['varType']` to `uint64_t` and use `maxBitwidth` for word-boundary/loop-count layout decisions while preserving the symbolic width key string for emitted expressions.

5. **Replace baked numeric constants with symbolic expressions in `fw_pack`/`fw_unpack`** in [builder/base/templates/systemc/structures.py](builder/base/templates/systemc/structures.py): In `get_unpack_mask_str` (~line 773), `fw_pack_setup` (~line 963), `fw_pack_oneVar` (~line 980), `fw_pack_oneNamedStruct` (~line 1020), and `fw_unpack` (~line 804): when a field's width or array size is parameterizable, replace integer literals for shifts, masks, and position increments with C++ symbolic expressions using the constant name (e.g., `(1ULL << WIDTH_CONST) - 1`, `WIDTH_CONST - 1`), mirroring the existing YAML `eval: "($N-1).bit_length()"` convention so emitted source text is invariant to the parameter value. For the `>64-bit` word-array path, use `maxBitwidth` to size the array at code-gen time but emit index expressions symbolically.

6. **Fix `_bitWidth`/`_byteWidth`/`_packedSt` struct declarations** in [builder/base/templates/systemc/structures.py](builder/base/templates/systemc/structures.py): In `oneStruct` (~lines 229–232), emit `_bitWidth` and `_byteWidth` using the symbolic constant name instead of the resolved integer `value['width']` when the struct is parameterizable. In `convertToType` (~line 64), add an `isParameterizable` path that always returns `uint64_t _packedSt` (or the correct word-array type based on `maxBitwidth`).

7. **Fix address-space sizing for registers and memories** in [builder/base/pysrc/processYaml.py](builder/base/pysrc/processYaml.py): In the address-allocation loop (~line 2486) where `size = roundup_pow2min4((row['width'] + 7) >> 3) * self.qualConstParse(row['wordLinesKey'])`, substitute `maxBitwidth` for `row['width']` and `maxValue` for `wordLines` when the struct width or word-line count is parameterizable, so allocated address space always accommodates the worst-case parameter. Update the register `bytes` field derivation (~line 963 in processYaml) similarly.

8. **Update SV type emitters** in [builder/base/templates/systemVerilog/constantsTypesEnumsStructures.py](builder/base/templates/systemVerilog/constantsTypesEnumsStructures.py) and [builder/base/templates/systemVerilog/package.py](builder/base/templates/systemVerilog/package.py): For parameterizable types, emit the typedef width using the symbolic constant name (already stored as `value['width']`) rather than `value['realwidth']`, so SV output is also text-stable.

### Further Considerations

1. **`ipParameters` context ordering**: the `ipParameters` section must be processed before any downstream YAML file that references its constants or types; confirm whether it must always appear in the top-level project file, or whether it can appear in any included file (with dependency ordering managed by the existing `processYamls` dependency graph).
2. **Transitive propagation depth**: the propagation pass must handle chains (e.g., a constant derived via `eval` from a parameterizable constant, used as the `width` of a type, used as the `arraySize` of a struct field). Confirm whether a single-pass graph walk suffices or whether iterative fixed-point convergence is needed for complex dependency chains.
3. **`maxBitwidth` enforcement policy**: the request says "direct assert in the IP" — confirm this means a hard generator-exit error (not a warning) when the resolved current value exceeds the declared `maxBitwidth`.
4. **Array-of-parameterizable-type compound case**: when both `arraySize` and element `bitwidth` are parameterizable, the `arraywidth = bitwidth * arraySize` expression in systemcGen.py (~line 146) must also be fully symbolic — confirm whether this is in scope for this phase or deferred.
