# Research: Block Registration Architecture Options

Date: 2026-05-04 (initial), 2026-05-05 (decision)
Status: decision recorded — **Option 9** with the factory-key extension to
`(blockType, variant, configTag)` is selected. Stage 0 prototype
validation is recorded in `../../proto/model` (`make step6`). See
"Decision and Rationale" at the end of the document.
Owner: T9 (`plan-development-ordering.md`)

This document is a working space for evaluating how `instanceFactory`
registration should be structured once blocks become class templates
(`template<typename Config>`). The original plan in
[`plan-block-registration.md`](./plan-block-registration.md) selected a
container-driven approach (Option 1); this document re-opened the design
space and the decision recorded here supersedes that plan.

The text-stability constraint, the parent→child encapsulation invariant,
and the transitive-registration requirement together rule out several
otherwise-attractive shapes. The point of this document is to make those
constraints explicit, lay out the option space, and surface the open
questions before any code change is made.

### Scope note: generated code

All block-level code under discussion (`<block>.h`, `<block>.cpp`,
`<block>.cppm`, container `.cpp`, project-level registration TUs) is
**generated**, not hand-written. The tradeoff axes that matter are
therefore architectural, not migration-cost-driven:

- **"Code change scope" is not a constraint.** Any of the options below
  can be implemented by changing the generators; no hand-written
  source needs to be edited as part of this work.
- **Backward compatibility of the *generated shape* is not required.**
  Existing examples will be regenerated. The only sources that must be
  preserved unchanged are the user-owned hand-written tail sections
  (e.g., the body inside `// GENERATED_CODE_END` markers in `cpu.cpp`),
  which do not currently contain registration code in any of the
  options below.
- **Migration cost framing in earlier drafts of this doc applied to
  hand-written `sc_main` files.** Today every example's `sc_main` /
  testbench is itself generated by `testbench.py`. So Option 4's
  "every `sc_main` must call a new init function" reduces to "modify
  one generator template," not "edit N hand-written files." The cost
  argument for Option 4 weakens correspondingly; see the updated
  Module-mode notes under that option.
- **Selecting between options should be driven by:**
  *(a)* correctness under the modules standard (static-init
  reachability),
  *(b)* parent→child encapsulation strength (constraint 2),
  *(c)* per-block text stability across project changes (constraint 1),
  *(d)* generator complexity and clarity of the generated artifact set,
  *(e)* runtime correctness for multi-Config-per-block (a separate
  factory-key concern).
- **Generated artifacts in the build directory are acceptable and
  not part of the user-visible surface.** Files generated into the
  project's `build/` tree (or equivalent) are not version-controlled,
  do not appear in the source tree, and are regenerated freely as
  the project's instance tree changes. Artifact-count concerns for
  build-directory files are weighted differently than for source-
  tree files: "one trampoline TU per parameterized block per
  project" is a meaningful cost in the source tree but not in
  `build/`. This reframing is what makes Option 9 viable, and it
  weakens the "no new project-level file" row in the summary matrix
  for Options 2A / 2C / 4 / 8 / 9 when their generated files are
  build-directory artifacts rather than source-tree files. It also
  weakens (without eliminating) the per-block-per-project artifact
  cost of Option 8 by moving the artifact out of the source tree.

The earlier "this is invasive" / "this is non-trivial migration"
language under Options 3 and 4 reflected an incorrect implicit
assumption that some affected files are hand-written. Those notes have
been retained for context but should be read as describing
*generator complexity*, not migration cost.

## Background

### Current behavior (pre-T9)

- `instanceFactory::registerBlock(blockType, factoryFn, variant)` is
  called from a static initializer in each block's `.cpp`. The
  initializer is a `static <className>::registerBlock <className>::registerBlock_;`
  definition triggered by an in-class struct/static pair generated by
  `classDecl.py` and `constructor.py`.
- The factory function is a lambda that calls
  `std::make_shared<<className>>(...)`. The lambda's TU is the block's
  own `.cpp`, which trivially has the full class definition.
- `instanceFactory::registerBlock` uses `std::map::emplace` internally,
  which is **first-write-wins** for duplicate keys (later calls are
  silently ignored).
- `createInstance(...)` is called from each container's constructor at
  runtime (after `main`), so static-init ordering across TUs does not
  matter.
- Container TUs include only the `<child>Base.h` headers; they never
  see the children's full class definitions. The lambda inside the
  child's `.cpp` is what actually calls `make_shared`. Container
  parallel-compilation is preserved.

### What changes when blocks become class templates

Three things break under the current pattern:

1. **Static-of-class-template hazard (B1).** A `static registerBlock
   registerBlock_;` declared inside a class template is a *declaration*
   without a generator-emitted definition. The static is never ODR-used
   in the current `ip_test` TUs (no one names
   `ip<Config>::registerBlock_`), so the link succeeds via lazy template
   instantiation; runtime then fails because the registrar constructor
   never ran. Adding an explicit definition is non-trivial because
   `<className>::registerBlock_` is itself a dependent type.
2. **Lambda hard-codes the Config (B2).** Even if the static were
   defined, today's lambda inside `<className>::registerBlock` reads
   `make_shared<<className><ipDefaultConfig>>(...)` regardless of
   `Config`. A non-default Config can never be reached through the
   factory.
3. **Per-Config enumeration is somebody's job, but who?** A project may
   bind `ip` to two Configs (`ipDefaultConfig`, `ipFastConfig`). At
   least one TU in the project must instantiate the lambda once per
   Config so that each `(block, Config)` factory entry exists at
   runtime. The current pattern's "block self-registers from its own
   `.cpp`" implicitly assumes one Config per block, and that assumption
   is what breaks.

### Constraints carried into T9

1. **Text stability per block.** A block's `.h` and `.cpp` contents must
   depend only on that block's own YAML. Adding/removing a Config to
   the project, or adding/removing an instance of the block, must not
   move text in the block's own files.
2. **Parent-container encapsulation.** Parent container TUs see only
   `<child>Base.h`. They do not include `<child>.h` and do not
   instantiate `<child><Config>`. This preserves parallel compilation
   and keeps internal block changes from triggering parent recompiles.
3. **Transitive coverage.** If `ip<Config>` instantiates `ipLeaf<Config>`
   internally (via `instanceFactory::createInstance("ipLeaf", ...)`),
   `ipLeaf<Config>` must be registered before `ip<Config>::ip(...)`
   runs. A scheme that only handles direct children of the top-level
   container fails as soon as the templated tree is more than one level
   deep.
4. **Idempotency across multiple registration sites.** Because
   `registerBlock` is `emplace`-based first-write-wins, calling the same
   `(block, Config)` registration multiple times is harmless. Schemes
   may rely on this, but should not depend on a specific *first* caller
   if the lambdas might differ (see "Conflicting lambdas" open
   question).
5. **Static-init ordering across TUs is irrelevant for correctness** so
   long as every registration TU's static runs before `main`. It is
   not safe to assume any particular order across TUs.
6. **`processYaml.py` already knows the project-wide instance tree** and
   the Config bound to each instance (via `getBlockData()`'s derived
   Config metadata). Schemes are free to use this data.
7. **Static-init reachability under modules.** This work is part of the
   ongoing C++20 modules transition (M3). Under classic headers, every
   TU that `#include`s a header containing a static initializer runs
   that initializer before `main`. Under modules, an `import` alone is
   not guaranteed to trigger the imported module's static initializers
   unless something from the module is referenced from the importing
   TU's compiled output. This affects which architectures stay
   correct-by-construction once blocks ship as `.cppm`. See
   "Modules-specific cross-cutting" below and the Module-mode notes
   under each option.

## Option Space

The options below differ along three axes:

- **Where the lambda is instantiated** (which TU has full child class
  visibility).
- **Where the per-project Config enumeration lives** (which generated
  artifact owns the `(block, Config)` set for the project).
- **What triggers registration at static-init time** (which static
  object's constructor runs).

### Option 1 — Container-driven registrar (current plan)

- Each block's `.h`/`.cppm` defines a free function template
  `register_<block>_variants<Config>()` whose body lists the block's
  variants and (per the recursion rule) calls into each templated
  child's registrar.
- Each container's `.cpp` emits an anonymous-namespace
  `_<container>_registrar` static whose constructor calls
  `register_<directChild>_variants<...>()` for each direct child.
- Transitive descendants are reached by per-block recursion.

**Encapsulation impact.** Each container TU instantiates
`register_<directChild>_variants<Config>()`, which means it must
instantiate the lambda body that calls `make_shared<child<Config>>`.
That requires the container TU to **`#include <child>.h`** (or
`import <child>;`), not just `<child>Base.h`. **This is a regression of
constraint 2.** Every parent TU now sees every direct child's full
class definition.

**Text stability per block.** Block `.h`/`.cppm` is text-stable (depends
only on the block's own YAML and its direct children's blocks).
Block `.cpp` loses its `registerBlock_` static — text-stable. ✓

**Transitive coverage.** Per-block recursion handles it. ✓

**Idempotency.** `emplace` first-write-wins covers redundant calls
across multiple containers. ✓

**Module-mode notes.** Under modules, every parent container `.cppm`
must `import <child>;` to reach the registrar template body, and the
child's class itself must be `export`ed for `make_shared<child<Config>>`
inside the lambda to compile in the parent TU. Selective export
(exporting only the registrar) does not help because the lambda body
is what reaches the class. The encapsulation regression therefore
*hardens* under modules: it becomes "every parent container module
imports every direct child module's full class," which forces a
project-wide module dependency graph that mirrors the instance
hierarchy. **Static-init reachability is satisfied** for this option
because each container TU is linked into the program (referenced from
`sc_main` or the testbench), so its registrar static is guaranteed to
run.

**Notes.** This is the option spelled out in `plan-block-registration.md`
today. The encapsulation regression is the reason this document
exists.

### Option 2A — Block self-registration; helper in header; project-level driver TU

- Each block's `.h`/`.cppm` defines an inline (templated) helper
  `_<block>_register_self<Config>()` (or non-templated for
  non-parameterized blocks). The helper body lists the block's own
  variants and calls `instanceFactory::registerBlock(...)`. **No
  recursion into children.**
- Each block's `.cpp` is text-stable; no registration code at all.
- A new project-level generated file, e.g.
  `<project>_registrations.cpp`, includes every block's full header
  and contains a single static whose constructor calls
  `_<block>_register_self<Config>()` once per `(block, Config)` pair
  the project's instance tree binds.

**Encapsulation impact.** Parent containers (`ip_top.cpp` and friends)
are unchanged: they continue to include only `<child>Base.h` and never
see the child's full class. The new project-level file is the *only*
TU that needs full visibility into every block, and it is purpose-built
for that role (analogous to a project's `main.cpp`). **Constraint 2
preserved.**

**Text stability per block.** Block `.h`/`.cppm` lists only that
block's own variants. Block `.cpp` has no registration code. **Both
are text-stable across project-wide Config additions.** ✓

**Project-level non-stability.** `<project>_registrations.cpp` does
change when the project's instance tree or Config bindings change.
That's the point: project-specific data lives in one purpose-built
file, not smeared across block files.

**Transitive coverage.** No per-block recursion is needed because the
project-level file enumerates *every* block in the project, including
deep descendants. `processYaml.py`'s instance walk already produces
this set. ✓

**Idempotency.** Trivially satisfied — each `(block, Config)` is called
exactly once from the project file. ✓

**Module-mode notes.** Under modules, the block's `.cppm` `export`s both
the class and the registrar helper template (or, with selective export,
exports only the helper while keeping the class module-internal — see
"Modules-specific cross-cutting" for that variant). The
project-registrations TU `import`s every block's module and calls each
helper. Because the project-registrations TU is *linked* into the
program (it owns the `_project_registrar` static), its static initializer
runs unconditionally, satisfying the static-init-reachability constraint.
This is the form best-supported by the modules standard: registration
is anchored to a TU that the build always pulls in, not to a side effect
of `import`.

**Notes.** Adds one new generated file per project. The block helper
template lives in the header / module so the project file can
instantiate it without seeing the block's `.cpp`.

### Option 2B — Block self-registration; helper in `.cpp`; explicit instantiation per Config

- Each block's `.cpp` defines `_<block>_register_self<Config>()` as a
  function template whose definition is *not* in the header.
- Each block's `.cpp` ends with `template void _<block>_register_self<C1>();`
  for each Config the project binds to that block.
- A small project-level driver TU (or each block's own `.cpp`'s anonymous
  static) calls the explicitly instantiated entry points.

**Encapsulation impact.** Block `.cpp` has full class visibility, so
the lambda compiles fine. No parent-container changes. **Constraint 2
preserved.** ✓

**Text stability per block.** **Fails.** The list of Config types at
the bottom of `<block>.cpp` is project-specific. Adding a Config to
the project changes `<block>.cpp` text. ✗

**Why include this option anyway.** It's the obvious "make it work
without a new file" approach and worth recording so it isn't
re-proposed. Reject on text stability.

**Module-mode notes.** Module mode does not improve this option.
The block module's implementation unit still needs the per-Config
explicit-instantiation list to compile the registrations, and that
list is still project-specific.

### Option 2C — Block self-registration; project file declares Config types only

- Same as 2A, except the helper template is defined in the block's
  `.cpp` (not the header), and the project-level file `extern`-declares
  the helper template specializations it needs and forces them via
  explicit instantiation declarations.
- Block `.cpp` emits the helper template definition once. Project file
  emits `extern template void _ip_register_self<ipDefaultConfig>();` and
  then calls it from a static.

**Encapsulation impact.** Parent containers unchanged. ✓

**Text stability per block.** Block `.cpp` defines the template
unconditionally; no per-project list. ✓ Block `.h` doesn't define the
template body; it only declares it. ✓

**Project-level non-stability.** Project file enumerates Configs as in
Option 2A. ✓

**Linking caveat.** `extern template` plus a call from the project file
relies on the block's `.cpp` having instantiated the specialization.
That requires the project file to also explicitly instantiate (in some
TU) the specialization, or for the block `.cpp` to do so. Either way,
*some* TU must list the Config set. If that TU is the project file
(`template void _ip_register_self<ipDefaultConfig>();` at file scope),
the block `.cpp` stays text-stable. ✓

**Notes.** Mechanically equivalent to 2A in its effect on per-block
text stability. The trade is between "template body in header"
(2A — header gets bigger, project file does instantiation by calling)
vs. "template body in `.cpp` with explicit instantiation in the project
file" (2C — header is leaner, project file does instantiation by
declaration). 2C is more conservative about header bloat and matches
the historical SystemC pattern of keeping bodies in `.cpp`. Worth
considering as a sub-form of the same architecture.

**Module-mode notes.** Modules dissolve much of the 2A vs. 2C trade.
A module implementation unit (`module ip;` without `export`) can host
the helper body, and the module interface unit (`export module ip;`)
exports only the declaration. The body is reachable to importers via
the linker, not via `extern template` machinery. So under modules, 2C
is the natural shape and 2A is a less-clean alternative that puts the
body in the interface unit. **Static-init reachability is satisfied**
the same way as 2A: the project-registrations TU is linked into the
program. Module partitions (e.g., `export module ip:registrar;`) can
further isolate the registrar's includes from the main class's
includes; cleaner builds, smaller invalidation scope.

### Option 3 — Per-block self-registration with type-erased Config dispatch

- Each block's `.cpp` registers itself for *every* Config the block's
  YAML names (typically just `<block>DefaultConfig`).
- The project's `instanceFactory::createInstance(...)` call passes a
  Config tag (string, integer, or `std::type_index`).
- The block's lambda body switches on the tag and dispatches to the
  correct `make_shared<block<Config>>`.

**Encapsulation impact.** Parent containers unchanged. ✓

**Text stability per block.** Block `.cpp` enumerates Configs, but only
those declared in the block's *own* YAML, not the project's. If a
project wanted to bind a Config the block hasn't declared, that's a
schema error. ✓ (depending on how Config types are declared per-block).

**Project-level non-stability.** Project file is unchanged from today;
no new project-level registrations file. ✓

**API impact.** `createInstance` signature changes (callers must supply
a Config tag, or the existing variant string is repurposed to encode
Config). All `createInstance` call sites change — but every
`createInstance` call site in the project is itself generated (from
`constructor.py`'s `subBlockInstances` walk), so this is a generator
change, not a hand-written-source migration.

**Type-system impact.** A switch on a runtime tag means each block's
`.cpp` must enumerate every Config it might be instantiated with at
generator time. The Config set then lives in the *block's* YAML,
not the project's instance tree. This shifts the source of truth.

**Notes.** Changes the public `createInstance` contract. The earlier
"invasive" framing reflected concern about hand-written callers; with
all callers generated, the relevant tradeoff is *type-system clarity*
(a runtime Config tag is weaker typing than a compile-time `Config`
template parameter) and *whether the source of truth for Config sets
should be the block's YAML or the project's instance tree*. Worth
considering only if the project-level file from 2A/2C is judged
architecturally undesirable.

**Module-mode notes.** Static-init reachability is the *real* problem
for this option under modules. The block's registration runs from a
static initializer inside the block's `.cpp` (or a module
implementation unit). For that initializer to fire, the block's
module's compiled output must be referenced by the program — typically
through `make_shared<block<DefaultConfig>>` somewhere in the link
graph. With type-erased dispatch, the parent container goes through
`createInstance` and never directly references the block's symbols
from its own TU. Whether the linker pulls in the block's TU therefore
depends on the build system and on whether some other linked TU
references the block. **This is fragile** and would need explicit
build-system support (e.g., a project-level "force-link these object
files" rule). Module mode worsens this option, not improves it.

### Option 4 — No registration at static init; explicit project-level init function

- Block files emit nothing at static init.
- The project-level generator emits a function
  `void <project>_register_all()` that calls each `(block, Config)`
  helper directly.
- `sc_main` (or the testbench) calls `<project>_register_all()` before
  `createTestBench(...)`.

**Encapsulation impact.** The project init function needs every block
header (same as 2A's project file). ✓ for parent containers.

**Text stability per block.** Block files have no registration code at
all. ✓

**Static-init dependency removed.** Registration ordering becomes
explicit and visible at the call site. Easier to debug than static
init.

**API impact.** Every `sc_main` (and potentially every standalone test
that uses `instanceFactory`) must call the new init function before
creating instances. Today's `sc_main` / testbench is itself generated
by `testbench.py`, so this is a single generator change rather than a
per-example edit; the migration-cost concern this option originally
carried does not apply. Hand-written tests outside the generated set
(if any) would need a one-line addition.

**Notes.** Architecturally cleanest in many ways; sidesteps every
static-init-order discussion. Without the migration-cost objection, the
remaining argument against Option 4 is whether registration-via-static
(invisible to user code) is preferred over registration-via-explicit-call
(visible at the call site). The former is what every option except
Option 4 produces; the latter is what Option 4 produces.

**Module-mode notes.** This is the option *most aligned with the
modules standard*. The static-init-reachability constraint that bites
Options 1 and 3 simply does not apply: registration is an explicit
function call, not a side effect of import or link. Block modules can
be `import`ed freely without worrying about whether their initializers
ran. The module dependency graph reduces to "the project init TU
imports every block module," which is exactly the same structure that
2A/2C need. The architectural delta from 2A/2C in module mode is
small — the trade is whether registration runs from a project-level
*static* (2A/2C) or from a project-level *function call* (4). The
latter is more explicit and easier to debug; the former is invisible
to user code. With code-change scope no longer a constraint (every
`sc_main` is itself generated), Option 4 is now competitive on its own
merits with 2A/2C; the choice between them rests on whether explicit
registration calls or static-init-driven registration is the better
end-state shape.

### Option 5 — Hybrid: non-templated blocks self-register; templated blocks via project file

- Non-templated blocks keep today's behavior unchanged (anonymous
  `static <className>::registerBlock <className>::registerBlock_;`
  in `<block>.cpp`).
- Templated blocks adopt Option 2A or 2C.
- The project-level registrations file enumerates only `(templatedBlock,
  Config)` pairs, omitting non-templated blocks.

**Encapsulation impact.** Parent containers unchanged. ✓

**Text stability per block.** ✓ for both kinds.

**Notes.** Smallest delta from today's working state for non-templated
projects. Mixed projects (e.g., `ip_test`) get a project file but it's
small. Migration of existing non-templated examples is zero. The cost
is two registration mechanisms in the codebase.

**Module-mode notes.** The non-templated half inherits the
static-init-reachability concern: a non-templated block that ships as
a `.cppm` and is reached only via `import` (not via direct symbol
reference) may not fire its self-registration static under the modules
standard. The templated half (which is 2A/2C-shaped) is fine because
the project-registrations TU is always linked. Two viable refinements:
(a) move *all* blocks to the project-file mechanism in module mode,
collapsing back to 2A/2C and giving up the "non-templated bit-for-bit
unchanged" property; (b) keep non-templated blocks in classic-header
form during the transition, so their static registration retains its
old guarantees, and migrate them to the project-file mechanism only
when they ship as `.cppm`. Option (b) is the natural M3 ordering.
A third refinement, Option 6a below, restores classic-header-style
linker reachability for module-form non-templated blocks via a
portable anchor pattern.

### Option 6 — Block-local self-registration of all block-declared variants

This option is the closest direct extension of today's
self-registration pattern. It shifts the source-of-truth for Config
sets from the project's instance tree to the block's own YAML, and
then repeats today's static-registration mechanism once per Config the
block declares.

- The block's YAML names every Config the block can be instantiated
  with (the existing `<block>DefaultConfig` plus any explicit
  variants). Configs become block-owned; projects pick among them by
  name rather than composing arbitrary Config types at the project
  level.
- Each block's `.cpp` (or module implementation unit) emits one static
  registrar per declared `(block, Config)` pair. Each registrar
  instantiates a typed lambda over `make_shared<block<Config>>` and
  registers under a distinct `(blockType, variant)` key.
- The project's instance tree refers to variants by the existing
  `variant` string. No project-level registrations TU is required.

**Encapsulation impact.** Parent containers unchanged — they include
only `<child>Base.h`. ✓

**Text stability per block.** Block `.h`/`.cppm` and `.cpp` enumerate
only Configs declared in the block's own YAML. Both files are
text-stable across project-wide additions. ✓

**Project-level non-stability.** None — no new project-level file. ✓

**Transitive coverage.** Each block self-registers its own variants
from its own TU. Deep descendants register independently as their TUs
are linked into the program. Per-block recursion is not required (the
recursion that Options 1 and 7 perform is replaced by per-block
self-registration in every TU). ✓ — subject to the static-init
reachability concern under modules; see below.

**API impact.** `createInstance`'s signature is unchanged. Variant
strings continue to drive selection. The existing
`(blockType, variant)` factory key naturally distinguishes
per-Config registrations because each Config maps to a distinct
variant.

**Multi-Config per block.** **Correct.** Distinct Configs map to
distinct variant strings, so each registers its own lambda under its
own key. No factory-key change is required to support multi-Config.

**Type-system impact.** Compile-time `Config` template parameter is
preserved end-to-end. No runtime tag dispatch inside the lambda
(unlike Option 3).

**Schema-rule cost.** Configs become block-owned. A project that wants
a novel Config for an existing block must declare it in that block's
YAML, not compose it freely at the project level. This is the same
source-of-truth shift discussed under Option 3, but applied at
compile time rather than at runtime tag-dispatch time. The trade is
*where* Configs are declared, not *how* they are typed.

**Module-mode notes.** Static-init reachability is the principal
concern. The block's static registrar lives in the block's own TU;
under modules, an `import <block>;` from a parent that only references
the base does not guarantee the linker pulls in the block's TU, and
the registrar may not fire. Without mitigation this is **fragile** in
the same way as Option 3. Option 6a below provides a portable
mitigation that moves this row from "fragile" to "safe" without
introducing a project-level TU.

**Notes.** This is the closest extension of today's self-registration
pattern: same mechanism, repeated once per declared Config. No new
generated file is introduced. The cost is concentrated in the schema
rule that Configs originate at the block, not the project.

### Option 6a — Force-link anchor in the base header (refinement)

> **Retired (2026-06-23).** Superseded by the Option δ retain attribute
> plus the build-system contract; see "Decision Addendum (2026-06-23):
> `force_link` retirement — Option δ selected". No base-header anchor
> symbol is adopted in the final design.

This is not a registration architecture in itself; it is a small
portable mechanism that restores classic-header-style linker
reachability for any option whose registration static lives in the
block's own TU. It applies to Options 3, 5 (non-templated half), and
6.

- `<block>Base.h` declares `extern int <block>_anchor;`.
- The block's `.cpp` / module implementation unit defines
  `int <block>_anchor = 0;`.
- `<block>Base.h` introduces an ODR-use of the anchor — for example
  via an inline variable initialised from its address:
  `inline int* <block>_anchor_use = &<block>_anchor;`.

Any TU that includes or imports `<block>Base.h` ODR-uses the anchor,
which forces the linker to pull in the block's TU. The block's
self-registration static then fires before `main`, mirroring the
classic-header guarantee. The mechanism is portable C++ and does not
rely on compiler-specific section attributes (`__attribute__((used))`,
`.init_array`, etc.) or build-system force-link rules.

**Effect on Options 3 / 5 (non-templated half) / 6.** Static-init
reachability under modules moves from "fragile" to "safe."

**Cost.** A single inline variable per block in the base header. The
anchor symbol is permanent in the base header but never appears in
user-facing API.

**Notes.** This refinement does not help Options 1, 2A, 2C, 4, or 7,
because those options already anchor their registration static in a
TU that is unconditionally linked (the parent container or the
project-level registrations / instantiation TU).

### Option 7 — Container-driven registration with a split-template factory

A variant of Option 1 that closes the parent-container encapsulation
regression by making the parent reference only a free-function
declaration, with the lambda body localised to the block's own TU.

- `<block>Base.h` declares a free function template
  `template<typename Config> std::shared_ptr<<block>Base>
   <block>_make(<ctor args>);` — declaration only, no body.
- The body of `<block>_make<Config>` is defined in the block's `.cpp`
  / module implementation unit, where full visibility into
  `<block><Config>` is available, and is the only place
  `make_shared<<block><Config>>` is compiled.
- A project-level TU `#include`s every block's full header (or
  `import`s every block's module) and emits one explicit instantiation
  per `(block, Config)` pair:
  `template std::shared_ptr<<block>Base> <block>_make<Config>(<ctor args>);`.
- The parent container's `.cpp` registers `&<child>_make<Config>` from
  an anonymous-namespace static, requiring only the declaration in
  `<child>Base.h`.

**Encapsulation impact.** Parent containers reference only the
declaration in `<child>Base.h` plus a free-function address. They
never instantiate the child's class and never see the child's full
class definition. **Constraint 2 preserved**, fixing Option 1's
regression. ✓

**Text stability per block.** Block `.h`/`.cppm` defines the primary
template body. Block `.cpp` / module implementation unit defines the
function template body. Neither lists project-bound Configs. ✓

**Project-level non-stability.** A project-level instantiation TU
enumerates the explicit instantiations, identical in role to Option
2A's project file. Project-specific data is concentrated in one
purpose-built TU.

**Transitive coverage.** As with Option 1, the parent container's
static registers its direct children. A parameterized child that
itself uses `createInstance` for templated grandchildren must
recursively trigger registration of the grandchildren under the
parent's bound Config. The recursion shape matches Option 1; the
difference is only that the lambda body is no longer co-located with
the parent.

**Module-mode notes.** Module dependencies for the parent container
reduce to `import <child>:base;` (or the equivalent partition shape).
The parent never imports the child's class module. The project-level
instantiation TU imports every block's full module. Static-init
reachability is satisfied because the parent container TU and the
project-level instantiation TU are both unconditionally linked.

**Notes.** This is a third variant of the project-TU family,
positioned between Options 1 and 2A. It keeps the registration static
in the parent container (Option 1's structural intent) while restoring
parent encapsulation (Option 2A's strength). The trade against 2A is
whether the registration static should physically live in the parent
or in the project-level TU; in module mode the practical difference is
small because both TUs are linked unconditionally.

### Option 8 — Per-block, per-project Config-binding header

A variant of Options 2B / 2C that preserves literal text stability of
the block's `.cpp` while permitting explicit instantiation within the
block's own TU.

- The block's `.cpp` contains a fixed
  `#include "<block>_project_configs.h"` line and consumes the
  included content via a typelist or fold expression to drive explicit
  instantiation and self-registration of each project-bound Config.
- `<block>_project_configs.h` is generated per project per block and
  lists the Configs the project's instance tree binds to that block.
- Block self-registration is preserved; no project-level registrations
  TU is required.

**Encapsulation impact.** Parent containers unchanged. ✓

**Text stability per block.** Literal text of the block's `.cpp` is
stable across project changes — only the included file's content
changes. The compilation *result* depends on the project. Whether
this satisfies constraint 1 is an interpretation question; under a
strict reading that constraint applies to "what the compiler sees,"
the option fails the constraint, the same as Option 2B.

**Project-level non-stability.** One generated header per block per
project. Artifact count grows linearly with `blocks × projects`
rather than `1 × projects` as in Options 2A / 2C / 4 / 7.

**Transitive coverage.** Each block independently consumes its own
binding header. ✓

**Module-mode notes.** The included `_project_configs.h` is a classic
header; under modules it would need to become a module fragment or be
replaced by a generated module partition per block per project. The
artifact-count concern compounds.

**Notes.** Recorded so that the option is not re-proposed. The
per-block-per-project artifact count and the borderline interpretation
of text stability make this weaker than Option 6 (which avoids the
project-specific artifact entirely) and weaker than Options 2A / 2C
(which concentrate project-specific data in one file rather than
distributing it across one-file-per-block). With the build-directory
generated-artifact preference recorded in the scope note above, the
artifact-count objection softens but the borderline text-stability
issue remains.

### Option 9 — Per-block-per-project trampoline TU (selected)

A refinement of Options 2A / 2C that splits the single project-level
registrations TU into one trampoline TU per parameterized block.

- For each parameterized block the project instantiates, a generator
  emits `<block>_<project>_registrar.cpp` (or a corresponding module
  implementation unit) into a generator-controlled artifact directory.
- Each trampoline TU is the **only** TU in the program that includes
  or imports the block's full class definition. Containers, the
  testbench, and other blocks see only `<child>Base.h`.
- The trampoline directly emits one `instanceFactory::registerBlock`
  lambda per `(block, variant, Config, configTag)` tuple and an
  anonymous-namespace static whose constructor performs those
  registrations. The lambda body names the concrete `block<Config>`
  type in the trampoline TU; no parameterized helper-template body is
  required from another `.cpp`.
- Block `.h`/`.cpp` are text-stable and contain no project-specific
  data. Parameterized blocks do not emit a templated registration
  helper; project-specific Config enumeration is entirely in the
  trampoline.
- The trampoline also carries verilated-variant registrations and
  tandem-pair registrations for the block when applicable. One
  trampoline per block is the single place where every
  project-specific registration concern for that block is reified.
- **Trampoline placement is a follow-on decision.** Three placements
  are viable:
  - The project's `build/` tree (regenerated, not version-controlled,
    invisible in the source tree).
  - A checked-in per-project IP-config directory (reviewable, diff-able
    in version control, regenerated by the generator on YAML changes).
  - A source-tree-adjacent location alongside the existing project
    files.
  The decision is intentionally deferred to the build-system refactor
  that accompanies the M3 modules transition; Option 9's mechanism
  does not depend on the placement.

**Encapsulation impact.** Containers unchanged. Each parameterized
block has exactly one TU in the program with full visibility into
its class — the trampoline. In the baseline module shape the block
class remains exported so an ordinary trampoline importer can legally
name `block<Config>`. Selective export remains a natural later
refinement, but if the class becomes module-internal the trampoline
must be generated as a module implementation unit or partition of the
block module rather than as a plain external importer. ✓

**Text stability per block.** Block `.h`/`.cppm` and `.cpp` depend
only on the block's own YAML. Project-specific Config enumeration is
in the trampoline, which is generated into `build/`. ✓

**Project-level non-stability.** N trampoline TUs per project (one
per parameterized block the project uses), all generated into
`build/`. Each trampoline is small (typically tens of lines) and
mechanical. None appear in the source tree.

**Transitive coverage.** The project's instance walk emits one
trampoline per parameterized block, including deep descendants. Each
trampoline registers its own block. Per-block recursion is not
required. ✓

**Module-mode notes.** Each trampoline TU is a regular `.cpp` (or
module implementation unit) that is unconditionally linked into the
program. Static-init reachability is satisfied by construction. The
baseline keeps the class exported for ordinary importing trampolines;
selective export requires the trampoline to be part of the block
module as an implementation unit or partition.

**Multi-Config per block.** Subject to the same factory-key
constraint as Options 2A / 2C / 4 / 7: distinct Configs registered
under the same `(blockType, variant)` key collide first-write-wins.
The factory-key extension to `(blockType, variant, configTag)`
resolves this for Option 9 and is committed to as part of the T9
selection (see "Decision and Rationale" at the end of the document).

**Verilated and tandem registration.** The trampoline absorbs all
project-specific registration concerns for the block, not only SC-only
Config registrations:

- **Verilated variants.** When the block has a verilated half (an SC
  wrapper around Verilator-compiled RTL), the trampoline references
  the per-variant `using` aliases produced by
  `<block>_hdl_sc_wrapper.h` and registers each variant under its
  `(blockType, variant, configTag)` key. This applies to every
  `hasVl` block, including wrappers whose SC model side is not
  Config-templated. Non-Config verilated wrappers use the
  `noConfigTag` sentinel. Wrapper-local `registerBlock_` emission is
  removed.
- **Tandem pairs.** Tandem verification pairs an RTL build with a
  model build for side-by-side comparison. The corresponding
  registration record is per-block and project-specific, which makes
  the trampoline the natural carrier. The exact record shape (a paired
  factory entry, a side-table, or a build-mode-selected entry) is a
  follow-on design decision for the plan stage.

**Comparison with related options.**

- **vs. Option 2A.** 2A consolidates registrations into one
  project-wide TU; Option 9 distributes them into one TU per block.
  Option 9 has finer build parallelism (changing one block's
  registration surface invalidates only its trampoline) and aligns naturally
  with per-block module boundaries. The cost is a higher artifact
  count (N vs 1), but in `build/` these are invisible.
- **vs. Option 2C.** 2C uses `extern template` declarations from a
  single project-level TU. Option 9 uses one TU per block; the
  module-implementation-unit refinement of 2C applies per-trampoline
  here.
- **vs. Option 7.** Option 7 keeps the registration *static* in the
  parent container with a project-level instantiation TU. Option 9
  moves the static into the per-block trampoline. The parent
  container in Option 9 has no registration code at all, only its
  own construction logic. Option 9 is therefore strictly less work
  for the container generator than Option 7.
- **vs. Option 8.** Option 8 emits per-block-per-project *headers*
  consumed by the block's own `.cpp`. Option 9 emits per-block-per-
  project *TUs* that consume the block's header. The block's `.cpp`
  stays text-stable in Option 9 (Option 8 violates this in
  compile-result terms). Build-directory placement removes the
  artifact-count objection from both, but Option 9 also restores
  literal text stability for the block's `.cpp`.

**Notes.** Under the build-directory preference recorded in the
scope note, Option 9 is the cleanest synthesis of the project-TU
family. It satisfies:

- per-block text stability (block files unchanged),
- parent encapsulation (baseline exported class, selective-export
  friendly when the trampoline is part of the block module),
- compile-time Config typing,
- static-init reachability under modules (trampolines are linked),
- minimal source-tree footprint (artifacts are invisible to users).

The remaining tradeoff against Option 6 (block-owned variants) is
schematic rather than mechanical: should Configs be declared at the
project or at the block? Option 9 supports project-composable
Configs naturally; Option 6 supports block-owned Configs naturally.
The mechanism question is settled by Option 9; the schema question
remains open.

## Modules-specific cross-cutting

C++20 modules change three things relevant to registration that headers
cannot express:

### Visibility decoupling between class and registrar

Under modules, `export module ip;` can choose, *per name*, what to
make visible to importers. Exporting the registrar template
(`export template<typename Config> void _ip_register_self();`) without
exporting the class itself is a legal and meaningful shape. An importer
gets a callable registrar but cannot directly construct
`ip<Config>` — `make_shared<ip<Config>>` won't compile in the importer
because the class is opaque.

The registrar's body, defined *inside* the same module unit, sees the
class because they share the module's internal namespace. The lambda
captured by the registration is constructed in module-internal code
and stored in the factory by base-class type. Callers retrieve it via
`createInstance(...)` and downcast to the base, never naming the class.

This is impossible under headers (a `#include` makes everything in the
header visible, including the class). Under modules it gives **stricter
encapsulation than today's pre-T9 invariant**: not only do parent
containers not include the child's class, the language itself prevents
them from naming it.

This shape is most useful for Option 2A (and 2C-as-2A-equivalent), and
unhelpful for Option 1 (the parent container needs the class to
instantiate the lambda body, regardless of what's exported).

### Static-init reachability

Under classic headers:

> Every TU that includes a header containing a static initializer runs
> that initializer before `main`. Period.

Under modules:

> An `import` does not guarantee the imported module's static
> initializers run unless something from the module is referenced from
> the importing TU's compiled output (i.e., the linker pulls in the
> module's object file).

This breaks the historical "self-registration via static-of-class-template
in `<block>.cpp`" pattern in module mode for any block that is imported
purely for its base class (as is typical: parent containers `import`
ripple through but only reference the base). The linker may not pull
in the block's `.cpp` / module implementation unit, so its static
initializer never runs.

Implications by option:

- **Option 1**: the *container* TU's static is what registers, and the
  container is referenced by the testbench, so the static fires. Safe.
- **Option 2A / 2C**: the *project-registrations* TU's static is what
  registers, and that TU is unconditionally linked. Safe.
- **Option 3**: the *block*'s static is what registers, and under
  modules the block's TU may not be linked. **Fragile** — would need
  build-system force-link rules to be reliable.
- **Option 4**: registration is an explicit call from `sc_main`. No
  static-init concern at all. **Safest**, at the cost of `sc_main`
  migration.
- **Option 5 (templated half)**: same as 2A. Safe.
- **Option 5 (non-templated half)**: same as Option 3 — fragile under
  modules unless the block stays in header form, moves to the project
  file, or is paired with Option 6a's force-link anchor.
- **Option 6**: the *block*'s static is what registers, same family as
  Option 3. **Fragile** by default; **safe** when paired with Option
  6a's force-link anchor in the base header.
- **Option 6a**: not a registration architecture — a portable
  force-link anchor that promotes Options 3 / 5 (non-templated half)
  / 6 from "fragile" to "safe" without introducing a project-level TU.
- **Option 7**: the *parent container* TU's static is what registers,
  and the container is referenced by the testbench, so the static
  fires. Safe.
- **Option 8**: the *block*'s static is what registers (same TU
  location as Option 6 / Option 5's non-templated half). **Fragile**
  by default; can be paired with Option 6a's anchor for the same
  promotion to "safe."
- **Option 9**: the *per-block trampoline* TU's static is what
  registers, and that TU is unconditionally linked into the program.
  Safe.

The static-init-reachability question is the strongest argument
*against* relying on per-block static registration in module mode. It
is the strongest argument *for* either (a) a project-level
registration TU (Options 2A / 2C / 4 / 7), which are correct by
construction under both headers and modules, or (b) pairing per-block
self-registration (Options 3 / 5 / 6 / 8) with Option 6a's anchor to
restore the classic-header reachability guarantee without introducing
a new project-level TU.

### Module implementation units and partitions

Modules introduce two layout tools that change "where the body lives":

- **Module implementation units.** A `module ip;` (no `export`) TU can
  define template bodies that are reachable to importers via the
  linker, without `extern template` machinery. This collapses the
  Option 2A vs. 2C distinction in module mode: 2C's "body in `.cpp`,
  declaration in header" pattern becomes "body in module
  implementation unit, declaration in module interface" — the same
  shape, but reachable across TUs without explicit instantiation
  declarations.
- **Module partitions.** `export module ip:registrar;` is a separate
  TU that participates in module `ip`. The registrar can live in its
  own partition, so the registrar's includes (e.g., `<algorithm>`,
  `<functional>`) are isolated from the class's includes. Cleaner
  builds, smaller invalidation scope when only the registrar changes.

These are refinements of how 2A/2C/4 are physically laid out, not new
options. They become available once M3 lands and are not options under
header mode.

### Header-form fallback during M3 transition

For Options 2A / 2C / 4, the project-level registrations TU needs to
work during M3 *while some blocks are still `.h` and others are
already `.cppm`*. A mix is fine: the project file can `#include
"<block>.h"` for header-form blocks and `import <block>;` for
module-form blocks. The project file is one of the few TUs that
already needs to span both worlds (along with `ip_top.cpp`, which
already does this for base-class headers vs. block modules), so it is
not a new burden.

## Cross-Cutting Considerations

### Where does the lambda body live?

Every option must answer: **which TU compiles
`make_shared<block<Config>>`?** The TU compiling the lambda body is the
TU that needs `<block>.h` (full class definition).

| Option | Lambda body TU | Needs full child class visibility | Class can stay module-internal |
|--------|----------------|-----------------------------------|--------------------------------|
| 1      | each parent container `.cpp` | every parent container | ✗ (parent needs class) |
| 2A     | project registrations TU | project registrations TU only | ✓ (only the registrar TU needs class; can use selective export) |
| 2B     | block's own `.cpp`       | block's own `.cpp` only (already true) | ✓ |
| 2C     | block's own `.cpp` / module implementation unit | block's own TU only (already true) | ✓ |
| 3      | block's own `.cpp`       | block's own `.cpp` only (already true) | ✓ |
| 4      | project init function TU | project init TU only | ✓ |
| 5      | block's own `.cpp` (non-templated) + project file (templated) | block + project file | ✓ |
| 6      | block's own `.cpp` / module implementation unit | block's own TU only (already true) | ✓ |
| 7      | block's own `.cpp` / module implementation unit (function template body) | block's own TU + project instantiation TU | ✓ (parent only needs declaration in `<child>Base.h`) |
| 8      | block's own `.cpp`       | block's own `.cpp` only (already true) | ✓ |
| 9      | per-block trampoline TU (build/) | per-block trampoline only | baseline exported class; selective export when trampoline is part of block module |

Options 2B/2C/3/5/6/8 keep visibility within the block's own TU,
matching today's invariant most closely. Option 7 keeps the lambda
body in the block's TU while still having a project-level
instantiation TU, but the parent container needs only a declaration —
the project-wide class visibility is concentrated in the
instantiation TU alone. Options 1, 2A, 4, and 5 (templated half)
require a separate TU to have project-wide visibility, but only
Options 2A, 4, 7, and 9 isolate that visibility to a *single*
purpose-built TU per block (Option 9) or per project (2A / 4 / 7).
Option 9 is uniquely strong on selective export: each block has
exactly one TU that needs the class, and that TU is the trampoline.
Under modules, the "Class can stay module-internal" column captures
the selective-export refinement available to every option except 1.

### Where does Config enumeration live?

| Option | Config set source              | Per-block YAML | Project YAML |
|--------|-------------------------------|----------------|--------------|
| 1      | container's instance tree     | partial        | yes          |
| 2A     | project instance tree         | no             | yes          |
| 2B     | block's `.cpp` (project list) | no             | leaks to block |
| 2C     | project instance tree         | no             | yes          |
| 3      | block's own YAML              | yes            | no           |
| 4      | project instance tree         | no             | yes          |
| 5      | block YAML (non-tmpl) + project tree (tmpl) | mixed | yes |
| 6      | block's own YAML              | yes            | no (project picks by name) |
| 7      | project instance tree         | no             | yes          |
| 8      | per-block-per-project header  | no             | leaks via included file |
| 9      | per-block trampoline TU (build/) | no          | yes (in trampoline only) |

Options 2A/2C/4/7/9 cleanly attribute Config enumeration to
project-level data, which matches where the data semantically lives
when projects compose Configs freely. Options 3/6 attribute Config
enumeration to the block's own YAML, which is correct when blocks own
their parameterizations and projects pick among them by name. The
choice between these two families is a schema-design question, not a
mechanism question.

### Lazy template instantiation interaction

Options 1, 2A, 2C, 4, 5 (templated half), 7, and 9 all rely on at
least one TU *explicitly* instantiating each `(block, Config)`
registration helper. Without that, lazy template instantiation will
skip the body and the registration never runs. The instantiating TU
and the requirement to list Configs explicitly is what binds these
options to a project-level artifact (one TU per project for 2A / 2C /
4 / 7, one TU per block per project for 9).

Options 2B, 3, 6, and 8 use explicit instantiation inside the block's
own `.cpp`, which is why they either leak project-level data into
per-block files (2B, 8) or move the source of truth into per-block
YAML (3, 6).

### Multi-Config per block

If two containers in the same project bind `ip` to different Configs
(`ip<ipDefaultConfig>` and `ip<ipFastConfig>`):

- Option 1 — each container registers its bound Config; first-write-wins
  on `(blockType, variant)` means the first container's Config sticks.
  Second container's instances dispatch through the first's lambda,
  which constructs the *wrong* Config. **Silent runtime bug.**
- Option 2A/2C/4/7 — project file (or instantiation TU) enumerates
  both `(ip, ipDefaultConfig)` and `(ip, ipFastConfig)`. They register
  under the same `(blockType, variant)` key and hit the same
  first-write-wins issue.
- Option 3 — Config tag is part of the dispatch, so different Configs
  go through different switch arms inside the same lambda. **Works
  correctly.**
- Option 5 — same as 2A for the templated half.
- Option 6 — distinct Configs map to distinct *variant strings* (one
  per declared Config in the block's YAML), so each registers under a
  distinct `(blockType, variant)` key. **Works correctly without a
  factory-key change.** This is a structural advantage of moving the
  Config source-of-truth into the block's YAML.
- Option 8 — same as 2A; project-bound Configs collide on the same
  `(blockType, variant)` key.
- Option 9 — selected with the factory-key extension; the per-block
  trampoline registers each Config under `(blockType, variant,
  configTag)`, so multi-Config-per-block works.

This is the underlying open question called out in
`plan-block-registration.md`'s "Multi-Config Per Block": no option in
the 2x / 7 / 9 family resolves it without changing the factory key
from `(blockType, variant)` to `(blockType, variant, configTag)`.
Options 3 and 6 sidestep the factory-key concern by construction —
Option 3 via runtime tag dispatch, Option 6 via mapping each Config
to its own variant string. The factory-key change for the 2x / 7 / 9
family is orthogonal to the option chosen here and can be deferred
until a project actually wants two Configs per block.

### Conflicting lambdas

If two TUs register the same `(blockType, variant)` with *different*
factory functions (e.g., a generator bug, or two blocks accidentally
sharing a name), the current `emplace`-based behavior silently keeps
the first and drops the second. None of the options surface this
automatically. A debug-build assertion in `instanceFactory::registerBlock`
keyed on the function target's type-erased identity would catch it,
independent of which option is chosen.

## Verilated block interaction

Verilated blocks — SystemC wrappers around Verilator-compiled
SystemVerilog RTL — sit outside the C++ template parameterization
path but interact with the same `instanceFactory` registration
mechanism. Their current shape informs the registration-architecture
choice and is informed by it.

### Current shape

- Per-variant SV wrapper files are generated, one per `(block,
  variant)`: `<block>_<variant>_hdl_sv_wrapper.sv`. Each wrapper
  instantiates the RTL DUT with concrete `#(.param(value))` overrides
  taken from the block's YAML `parameters` section. Verilator
  compiles each wrapper independently, producing per-variant C++
  classes `V<block>_<variant>_hdl_sv_wrapper.h`.
- A single SC wrapper header `<block>_hdl_sc_wrapper.h` defines a
  class template `<block>_hdl_sc_wrapper<DUT_T>` and per-variant
  `using` aliases of the form
  `using <block>_<variant>_hdl_sc_wrapper = <block>_hdl_sc_wrapper<V<block>_<variant>_hdl_sv_wrapper>;`.
- The SC wrapper carries the today-style
  `static registerBlock registerBlock_;` and registers each variant
  under a distinct `(blockType, variant)` factory key. The lambda
  body references the per-variant `using` alias and constructs
  `<block>_<variant>_hdl_sc_wrapper`.
- Verilator does **not** produce a parameterized C++ class. Each
  `(SV module, parameter set)` becomes a separate Verilator
  invocation with a unique output prefix. Per Verilator 5.047
  documentation (April 2026), output prefixes must be unique per
  parameter set, and the N-classes-per-N-variants shape persists.
  Hierarchical Verilation (`--hier-block`) and the recent
  type-parameter support for hierarchy blocks parallelise these
  invocations but do not collapse the per-variant fan-out into a
  single C++ class.

The SC wrapper is templated on the DUT type, not on a Config policy.
Variants are reified at SV-wrapper-generation time and crystallised
into distinct DUT types; they are not C++ template parameters of the
SC wrapper itself. The SC class template exists only to bind the
wrapper body to whichever Verilator-compiled DUT type the variant
selected.

### Why the per-variant fan-out is "klugy" and what would change it

The fan-out is a consequence of Verilator producing one C++ class per
SV-parameter set, not of the registration architecture. The
per-variant SV wrapper is the boundary that converts the project's
"variant by name" abstraction into Verilator's "unique output prefix"
requirement. Two upstream developments would reduce the cost:

- **Verilator emitting a parameterized C++ class** for a parameterized
  SV module. Not on the current roadmap. If it ever lands, the SC
  wrapper would become directly templated on the SV parameter values,
  the per-variant SV wrapper files would disappear, and the
  registration architecture would converge on the SC-only-templated
  shape (one of Options 2A / 2C / 6 / 7, depending on the chosen
  source-of-truth for variants).
- **SV-2012 parameterized packages with broad EDA tool support.**
  Recorded as a future follow-up in `plan-sv-parameterization.md`.
  Adoption would let one set of package text serve multiple variants
  in a single elaboration, but would not eliminate the per-variant
  Verilator output unless paired with the previous bullet.

Neither development is imminent. The per-variant SV wrapper artifact
should be planned around, not designed away.

### Interaction with each registration option

- **Options 2A / 2C / 4 / 7.** The project-level registrations TU
  enumerates `(verilatedBlock, variant)` pairs alongside
  `(scBlock, Config)` pairs. The two enumerations share a single
  driver TU and use the same `instanceFactory` API — the factory key
  `(blockType, variant)` is uniform across both kinds of block. This
  is the cleanest fit for the verilated side because the project's
  instance tree is the natural source of truth for which variants
  are in use.
- **Option 9.** Each verilated block gets its own trampoline TU in
  `build/`, mirroring the per-parameterized-SC-block trampoline
  shape. The trampoline imports the verilated SC wrapper header,
  references the per-variant `using` aliases, and registers each
  variant. The verilated and SC-only sides use the same per-block
  trampoline mechanism; the only difference is what the trampoline
  enumerates (per-variant `using` aliases for verilated blocks,
  direct per-Config lambdas for SC-only blocks). This is
  the most uniform fit between the two sides under the project-TU
  family.
- **Option 1.** The parent container TU instantiates each direct
  child's registrar. For a verilated child, the parent's `.cpp` must
  `#include "<child>_hdl_sc_wrapper.h"` and reference the per-variant
  `using` aliases. The parent-encapsulation regression is identical
  to the SC-only case.
- **Option 3.** Type-erased Config dispatch does not fit verilated
  blocks. Variants are not Config types; they are distinct DUT C++
  classes produced by separate Verilator runs. The lambda body for
  each verilated variant must reference its specific `using` alias,
  which is a static dispatch already.
- **Option 6.** The verilated-block side is **already doing
  Option-6-shaped registration today**: variants are declared in the
  block's own YAML, the SC wrapper self-registers each variant under
  a distinct `(blockType, variant)` key, and the block's TU carries
  the registration code. Adopting Option 6 for SC-only-templated
  blocks would unify the two sides under a single mechanism:
  SC-only Configs and verilated variants both become
  "block-declared variants picked by the project by name."
- **Option 6a.** Applies equally to verilated blocks if their SC
  wrapper TU is reached only via `import` under modules. The
  force-link anchor in `<block>Base.h` covers both verilated and
  SC-only blocks without modification.
- **Option 8.** The per-block-per-project header pattern is already
  present in spirit on the verilated side as the per-variant SV
  wrapper fan-out. That the verilated side accepts this artifact
  count does not justify accepting it on the SC-only side, because
  the verilated cost is forced by Verilator's output shape and the
  SC-only cost is not.

### Alignment recommendation

The verilated side does *not* favour any option in the summary
matrix on its own merits; it is structurally neutral. Its
per-variant artifacts are determined by Verilator, not by the
registration architecture.

What the verilated side *does* offer is a precedent: today's
variant model on the verilated side is block-owned (Option 6 in
spirit), and projects pick variants by name. If the SC-only side
adopts Option 6, the two mechanisms align under one shape — every
block declares its variants in YAML, every block self-registers,
the project's instance tree picks variants by name, and no
project-level registrations TU is needed for either kind of block.

If the SC-only side adopts Options 2A / 2C / 4 / 7 instead, the
project-level TU absorbs verilated registrations alongside SC ones
without conflict. The verilated side neither gains nor loses
anything from this choice; the project TU simply lists both kinds
of `(blockType, variant)` pair in one place.

If the SC-only side adopts Option 9, both kinds of block use the
same per-block trampoline mechanism in `build/`. This is the most
uniform mechanical fit: the generator emits one trampoline per
parameterized block regardless of whether the parameterization is a
C++ Config template or a Verilator-driven variant set. The schema
question (project-composable Configs versus block-owned Configs)
remains separate; Option 9 supports project-composable Configs and
also supports block-owned variants on the verilated side, mirroring
today's behaviour.

The verilated side therefore does not constrain the SC-only choice,
but the precedent of block-owned variants on the verilated side is
worth weighing as evidence that the Option 6 schema is already
familiar in this codebase.

## Open Questions

1. **Is one new generated file per project (Options 2A/2C/4) acceptable**
   given that `processYaml.py` already produces project-wide data?
2. **For Option 2A vs. 2C**, which is preferred — template body in the
   header (2A: simpler call site, larger header) or template body in
   `.cpp` with `extern template` declarations (2C: leaner header,
   slightly more generator complexity)?
3. **Is changing `createInstance`'s signature to take a Config tag
   (Option 3) acceptable** as a generated-API change, or does the
   weaker typing (runtime tag vs. compile-time `Config`) and the
   relocation of the source-of-truth (block YAML vs. project tree)
   rule it out architecturally?
4. **For Option 4**, with `sc_main` migration reduced to a generator
   change, the original objection (per-example hand edits) no longer
   applies. Is explicit registration-via-function-call preferred over
   registration-via-static-init for an end-state design?
5. **Multi-Config-per-block factory key change — resolved.** T9
   commits to `(blockType, variant, configTag)` now. The Stage 0
   prototype validates the key extension and same-Config variant
   fallback behavior.
6. **Hybrid (Option 5)**: with code-change scope no longer a constraint,
   the original "smallest delta from today" argument for Option 5 is
   weaker. Is there still value in keeping two registration mechanisms
   (one for non-templated, one for templated) given the static-init-
   reachability fragility of the non-templated half under modules, or
   should every block move to a single mechanism for uniformity?
7. **Where does `addParam` live?** Independent of registration
   architecture, the per-variant parameter table (`addParam`) is
   Config-independent. Does it stay folded into the registration
   helper, or does it move to its own non-templated function called
   from the same place as the registrations?
8. **Modules-driven preference.** The static-init-reachability
   constraint under modules (constraint 7) makes Options 1 / 2A / 2C /
   4 / 7 / 9 correct by construction and Options 3 / 5 (non-templated
   half) / 6 / 8 fragile in module mode unless paired with Option 6a's
   force-link anchor. Combined with the visibility-decoupling
   capability that favors 2A / 2C / 4 / 7 / 9, does this push the
   choice strongly toward a project-level registration TU, or is the
   per-block self-registration shape (Options 3 / 6 plus 6a) still
   competitive for its lack of a project-level artifact?
9. **Selective export adoption.** If a project-level registration TU is
   chosen, do we want to take advantage of selective export to make the
   block class itself module-internal (visible only to its own module
   and the registrar), or keep the class exported for parity with the
   header-mode shape during the transition?
10. **Source-of-truth for Configs (Option 6 vs. project-TU options).**
    Should Configs be block-owned (declared in each block's YAML, with
    projects picking variants by name — Options 3 and 6) or
    project-composable (declared at the project level and bound to
    blocks by the instance tree — Options 2A / 2C / 4 / 7)? This is
    a schema-design question that is independent of the registration
    mechanism but determines which option family is viable.
11. **Force-link anchor adoption (Option 6a).** *Resolved
    (2026-06-23): no anchor adopted.* See the Decision Addendum —
    reachability is the Option δ retain attribute for direct-`.o`
    linking plus the build-system contract for archives, so no
    base-header anchor symbol is added. (Original question: if Option 6
    is selected, is the inline force-link anchor in `<block>Base.h`
    acceptable as a permanent base-header surface element? It is
    portable C++ and small, but it adds a module-internal symbol to
    the public base-header API. The same question applies if Options
    3, 5 (non-templated half), or 8 are paired with 6a.)
12. **Schema constraint enforcement.** If Option 6 is selected, where
    is the rule "every Config used by a project must be declared in
    the corresponding block's YAML" enforced? `processYaml.py` is the
    natural place; the failure mode if the rule is violated is a
    missing-variant runtime error in `instanceFactory::createInstance`.
13. **Option 7 vs. Option 2A.** Both require a project-level TU.
    Option 7 hosts the registration *static* in the parent container
    (matching Option 1's structural intent) while delegating the
    explicit-instantiation list to the project TU. Option 2A hosts
    both in the project TU. Is there architectural value in
    separating these responsibilities, or does concentrating both in
    the project TU produce a cleaner artifact set?
14. **Verilated-block alignment.** The verilated side already follows
    a block-owned-variant model (Option 6 in spirit) because
    Verilator produces N distinct C++ classes for N parameter sets.
    Should the SC-only side align with that precedent (adopt Option
    6, accept block-owned Configs, unify both sides under one
    mechanism), or should the two sides remain in different shapes
    (project-TU-driven SC-only registration alongside block-owned
    verilated variants)? This is a uniformity question; both shapes
    work, but mixing them means two mental models for "how does a
    new block get registered."
15. **Future Verilator improvements.** If Verilator gains
    parameterized-C++-class output (not currently on the roadmap as
    of Verilator 5.047, April 2026), the per-variant SV wrapper fan-
    out collapses and the verilated SC wrapper becomes directly
    templated on SV parameter values. At that point the verilated
    side becomes structurally equivalent to the SC-only-templated
    side. Should the registration architecture chosen now anticipate
    this convergence (favour an option that unifies cleanly under
    that future shape), or should it be optimised for today's
    klugy-but-stable per-variant artifact?
16. **Trampoline placement (Option 9).** The trampoline mechanism is
    settled, but the placement of the generated TUs is not. Three
    candidates are viable: (a) the project's `build/` tree
    (regenerated, not version-controlled), (b) a checked-in
    per-project IP-config directory (reviewable, diff-able in version
    control), or (c) a source-tree-adjacent location alongside other
    project files. The decision is deferred to the build-system
    refactor that accompanies the M3 transition. Practical
    generator-complexity concerns (naming collisions across projects,
    regeneration triggers, build-system wiring) need to be addressed
    regardless of placement and are tracked in the new
    [`plan-block-registration.md`](./plan-block-registration.md).
17. **Option 9 vs. Option 6 final selection — resolved.** The schema
    family question was settled in favour of project-composable Configs
    on the following grounds (see "Decision and Rationale"):
    - Configs vary types and structures, not only data values, which
      argues for compile-time `Config` template parameters rather than
      block-YAML-enumerated variants.
    - Named variants are project-specific in the team's operating
      model: an IP defines the supported range of configurations and
      features, and projects select specific configurations as
      required. Enumerating the project's named variants in each
      block's YAML would smear project data into block files and
      violate the per-block text-stability constraint that motivated
      this work.
    Option 6 is therefore not viable. The selected mechanism is
    Option 9 with the factory-key extension committed to as part of
    the same change. The schema decision is recorded; the open
    questions that remain are mechanical (placement, naming, module
    layout) and are tracked in the new
    [`plan-block-registration.md`](./plan-block-registration.md).

## Decision and Rationale (2026-05-05)

### Selected option

**Option 9** — per-block-per-project trampoline TU — is selected.
Each parameterized block in a project receives one generated trampoline
TU that:

- Includes or imports the block's full class definition (the only TU
  in the program that does so under the modules-mode selective-export
  refinement).
- Emits direct `instanceFactory::registerBlock(...)` lambdas for each
  `(block, variant, Config, configTag)` tuple the project's instance
  tree binds. No parameterized helper-template body is required from
  another TU.
- Carries an anonymous-namespace static whose constructor performs
  those registrations.
- Carries verilated-variant registrations and tandem-pair
  registrations for the block where applicable.

### Schema family

Project-composable Configs are selected. Named variants are
project-specific; the IP defines the range of configurations and
features it supports, and projects pick from that range. Configs may
vary constants, types, and structures, which mandates compile-time
`Config` template parameters and rules out the runtime tag dispatch
of Option 3.

### Factory-key extension

The factory key is extended from `(blockType, variant)` to
`(blockType, variant, configTag)`. The Stage 0 prototype selected a
generator-assigned stable string tag plus a reserved
`instanceFactory::noConfigTag` sentinel for non-templated callers. All
`createInstance` callers are in generated code, so the change is
mechanically tractable.

### Rationale, by constraint

- **Per-block text stability** (constraint 1) — satisfied. Block
  `.h` and `.cpp` depend only on the block's own YAML; project-specific
  Config enumeration lives in the trampoline.
- **Parent-container encapsulation** (constraint 2) — satisfied.
  Parent containers see only `<child>Base.h`. Baseline module mode
  keeps the block class exported for ordinary importing trampolines;
  selective export remains a follow-up when the trampoline is generated
  as a module implementation unit or partition.
- **Transitive coverage** (constraint 3) — satisfied. The project's
  instance walk emits one trampoline per parameterized block,
  including deep descendants. No per-block recursion is required.
- **Idempotency** (constraint 4) — satisfied. Each
  `(block, variant, Config, configTag)` tuple is registered exactly
  once from a single trampoline.
- **Static-init ordering** (constraint 5) — irrelevant by design.
- **Static-init reachability under modules** (constraint 7) —
  satisfied by construction. Each trampoline TU is unconditionally
  linked into the program.

### Rejected options, in summary

- **Option 1** rejected on parent-container encapsulation regression
  (every parent TU would see every direct child's full class).
- **Option 2B** rejected on text stability (block `.cpp` would carry
  a project-specific Config list).
- **Option 3** rejected on type-system grounds: runtime tag dispatch
  cannot select between distinct policy types that vary structures
  and types.
- **Option 4** competitive on technical merits but loses to Option 9
  on encapsulation strength under selective export and on the
  invisibility-of-registration-trigger style preference (soft).
- **Option 5** rejected as a hybrid; with code-change scope no longer
  a constraint, the original "smallest delta from today" argument
  is gone.
- **Option 6** (and 6a) rejected because variants are project-specific
  in this team's operating model. Block-YAML enumeration of
  project-named variants would smear project data into block files.
- **Option 7** loses to Option 9 on artifact concentration: Option 7
  splits the registration static (in the parent container) from the
  explicit-instantiation list (in a project-level TU); Option 9
  concentrates both in the per-block trampoline, which is
  architecturally simpler.
- **Option 8** rejected on text stability (project-specific included
  header smears project data into the block's compilation).

### Items deferred to the plan stage

The core C++ mechanics are settled and prototyped by
`make -C ../../proto/model step6`. The following implementation-layout
items are tracked in the new
[`plan-block-registration.md`](./plan-block-registration.md):

- **Trampoline placement.** `build/` vs. checked-in IP-config
  directory vs. source-tree-adjacent. Tied to the M3 build-system
  refactor.
- **Trampoline naming convention.** Avoids collisions across projects.
- **Module unit shape.** Plain `.cpp`, module implementation unit,
  or module partition. Affects selective-export ergonomics.
- **Selective export adoption.** Whether the block class becomes
  module-internal during the M3 transition or stays exported for
  parity with header-mode.
- **Config policy type location.** Where Configs are defined and how
  the trampoline reaches them.
- **Generator architecture.** Which generator emits the trampolines,
  and the regeneration triggers.
- **`configTag` encoding.** Settled as a generator-assigned stable
  string plus the `instanceFactory::noConfigTag` sentinel.
- **`addParam` placement.** Folded into the registration helper or
  split into a non-templated companion.
- **Tandem registration record shape.** Paired factory entry,
  side-table, or build-mode-selected entry.

## Decision Addendum (2026-06-23): `force_link` retirement — Option δ selected

This addendum closes the `force_link` follow-up tracked by
[`plan-registration-encapsulation-cleanup.md`](./plan-registration-encapsulation-cleanup.md).
The 2026-05-05 decision above (Option 9 for parameterized blocks) is
unchanged. This entry only governs the **non-templated SC block and
testbench-top** registration trigger, which the T9 plan left on an
active `force_link_<block>()` function.

### Selected option

**Option δ** — self-registering static in the block's own `.cpp`,
marked with a portable retain attribute, plus an explicit build-system
contract for archive packaging. `force_link_<block>()` /
`force_link_<B>Testbench()` declarations, definitions, and all
call-site emissions are **retired**. Option α (universal per-block
trampoline) was held as the fallback and is not needed: the δ proto
matrix validated cleanly.

### Why δ over α

- Smallest footprint: no new TUs (α adds one per non-templated block).
- Restores the source-level encapsulation contract fully — parents and
  the testbench have zero compile-time symbol references to
  non-templated children.
- Current production builds (every `examples/*` Makefile and the
  `debayer` project) link block `.o` files directly, which already
  satisfies δ's runtime prerequisite with no build-system change.

### Mechanism

- `common/systemc/instanceFactory.h` defines `A2C_REGISTRATION_RETAIN`,
  expanding to `[[gnu::used, gnu::retain]]` on GCC/Clang and to nothing
  on toolchains that must rely on the build-system contract alone.
- The generator applies `A2C_REGISTRATION_RETAIN` to each
  `_<block>_registered` self-registering static
  (`constructor.py`, `testbench.py`, `blockRegs.py`) and drops every
  `force_link` declaration/definition/call
  (`constructor.py`, `baseClassDecl.py`, `testbench.py`, `blockRegs.py`,
  `fileGen.py`).

### Proto matrix results (W7 + W2 tandem)

Driver: `proto/model/test/delta_matrix.sh` (with
`block_registration_delta*.{h,cpp,cppm}` and the tandem-shaped
`block_registration_delta_tandem.*` / `test_block_registration_delta_tandem.cpp`).
Toolchains exercised: **clang 20.1.8** and **gcc 13.1.0**.
All rows matched expectations (`MATRIX RESULT: all configurations
matched expectations`).

### Findings

1. **Direct-`.o` linking is sufficient on both toolchains.** A `.o`
   named on the link line is a GC root, so its `.init_array` entry
   survives even `--gc-sections` and even *without* the retain
   attribute (D1c, T1b both PASS). The attribute is therefore
   belt-and-suspenders for the direct-`.o` shape and the genuine
   guard for any future configuration that GCs the object.
2. **The build-system contract is load-bearing only for archive
   packaging.** D2 (archive, no flag) fails as expected because no
   symbol references the member; D3 (`--whole-archive`) and D4
   (`-Wl,-u,<anchor>`) both recover it. No source-level pragma can
   override the archive-extraction rule, which is exactly why δ makes
   this a documented build-system contract rather than a per-call-site
   `force_link`.
3. **Modules mode is fine (D5).** A directly-linked module object's
   self-registering static fires under the same `-fmodule-file=` /
   `--precompile` flags the examples use.
4. **Tandem inherits δ transitively (W2 → T1/T1b/T2).** The
   tandem-shaped proto builds a `<block>Tandem` wrapper that, through
   the factory only (no `force_link`), constructs both the `_verif`
   (registrar static) and the non-templated `_model` (δ static). It
   passes on direct-`.o` for clang+gcc (T1) and in modules mode for
   clang (T2). This closes the W2 gap the Stage 0 prototype never
   exercised.

### Build-system contract

Projects that link SC block objects directly (every `examples/*`
Makefile and the `debayer` project today) need **no** additional flag.
A project that packages SC blocks into a static archive **must** apply
`-Wl,--whole-archive` (GNU/LLVM), `-force_load` (Apple ld64), or
`/WHOLEARCHIVE:` (MSVC link) to that archive, or add an explicit
`-Wl,-u,<registration-anchor>` per archived block.

### Scope / coverage notes

- All eight `examples/*` projects regenerate with **zero** `force_link`
  emission and build+run without regression under δ.
- Regenerating the `debayer` project also yields zero `force_link`. A
  *live* `debayer` tandem run is currently blocked by an **unrelated**
  in-progress migration (the project's uncommitted `yamlFormat: 2`
  switch makes base headers emit `import shared_types;` while no
  matching `.cppm` is generated yet — the WI6 cppm-include-contract
  gap, owned by `plan-cppm-include-contract-cleanup.md`). That gap
  fails the *first* compiled TU, well before anything tandem-specific,
  and is independent of δ. Tandem coverage for δ is therefore provided
  by the tandem-shaped proto (T1/T2) above rather than a live debayer
  run.

### Cross-references

- **Option 6a** (passive force-link anchor in `<block>Base.h`) and the
  active `force_link` function the Stage 0 prototype promoted: both are
  **retired** by this decision in favour of the δ retain attribute plus
  the build-system contract. The encapsulation property Option 6a tried
  to preserve is now achieved without any parent-visible anchor symbol.
- **Open Question 11** (force-link anchor adoption): resolved — no
  source-level anchor is adopted; reachability is the retain attribute
  (direct-`.o`) plus the build-system contract (archives).
