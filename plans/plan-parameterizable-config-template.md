## Plan: Parameterizable Types and Structures via Config Policy Template

**Status:** historical; superseded for current execution. Use
`plan-variant-config-unification.md` for the current variant/Config
owner, `plan-param-constant-collision.md` for parameter/SV collision
work, and `plan-eval-symbolic-emission.md` for active symbolic-eval
execution.

This plan implements the recommended approach from `plan-ip-namespaces-and-parameterization.md` Sections 4.5–4.6: **Option P2 (Config policy template) combined with the P1 symbolic-expression foundation**. It covers Phase 2 (text-stable Config-templated IP code) and the generation-side portion of Phase 3 (per-instance Config struct generation).

The goal: the same generated IP source files work unchanged for any valid parameter configuration. Different configurations are expressed through different Config structs, and the C++ type system (templates) handles multi-instance coexistence.

### Relationship to the parent plan

This plan implements the following sections of `plan-ip-namespaces-and-parameterization.md`:

- **Section 4.2 (P1):** `ipParameters` YAML schema, `isParameterizable` transitive propagation, `maxBitwidth`/`maxValue` constraints — the YAML-level infrastructure.
- **Section 4.5–4.6 (P2):** Config policy template pattern for C++. All parameterizable types/structs/blocks become `template<typename Config>`. Constants are referenced as `Config::CONSTANT_NAME`.
- **Section 4.6 "Underlying C++ Type Strategy":** Fixed `uint64_t` for parameterizable types and `_packedSt`.
- **Section 4.6 "Making Pack/Unpack Text-Stable":** Symbolic `Config::` expressions for shifts, masks, positions.
- **Section 4.6 "Template Method Implementations":** Header-only requirement for parameterizable structs.
- **Section 5 (Address Decoding):** Worst-case sizing via `maxBitwidth`/`maxValue`, named-constant references in decode logic.

It does **not** cover:
- Namespaces (Phase 1) — addressed separately.
- `instanceFactory` template registration (Phase 3 runtime) — deferred.
- IP packaging (Phase 4) — deferred.
- C++ modules (Section 6) — deferred pending prototype.
- SV parameterization strategy (Section 4.3) — deferred pending EDA tool validation.

### Steps

#### Step 1: Add `ipParameters` section to the schema

**File:** [builder/base/config/schema.yaml](builder/base/config/schema.yaml)

Add a new top-level `ipParameters` node. Its body contains `constants` and `types` sub-sections that mirror the existing schema nodes (lines 69–102), with additional constraint fields:

```yaml
ipParameters:
  constants:
    constant: key
    value: eval
    desc: required
    maxValue: required        # Maximum value this constant can take across all parameterizations
    valueType:
      _type: optional(uint)
      _validate:
        values:
          - uint
          - int
  types:
    type: key
    desc: required
    isSigned: optional(false)
    maxBitwidth: required     # Maximum bitwidth this type can have across all parameterizations
    width: optionalConst()
    widthLog2: optionalConst()
    widthLog2minus1: optionalConst()
```

Also extend the existing `constants` node (line 69) with:
```yaml
  isParameterizable: optional(false)
  maxValue: optional(0)
```

And extend the existing `types` node (line 90) with:
```yaml
  isParameterizable: optional(false)
  maxBitwidth: optional(0)
```

These follow the same `optional(default)` pattern as `isSigned: optional(false)` at line 94.

#### Step 2: Process `ipParameters` as an embedded context in processYaml

**File:** [builder/base/pysrc/processYaml.py](builder/base/pysrc/processYaml.py)

In `processSingleFile` (line 2793), detect the `ipParameters` section. Feed its `constants` and `types` sub-data through the existing `processSection` pipeline (line 2832) under a dedicated `_ipParameters` context. After processing, stamp every resulting entry with `isParameterizable=True` and copy the declared `maxValue`/`maxBitwidth` onto the entry in `self.data`.

#### Step 3: Transitive propagation of `isParameterizable`

**File:** [builder/base/pysrc/processYaml.py](builder/base/pysrc/processYaml.py)

After all YAML files are loaded, run a transitive propagation pass over `self.data['constants']`, `self.data['types']`, and `self.data['structures']`:

1. Mark a **constant** as parameterizable if its `value` expression (eval) references any parameterizable constant.
2. Mark a **type** as parameterizable if its `width`, `widthLog2`, or `widthLog2minus1` resolves through a parameterizable constant.
3. Mark a **structure** as parameterizable if any constituent field's type, subStruct, or `arraySize` is parameterizable.
4. Compute `maxBitwidth` for derived entries: for types, resolve width using `maxValue` of the underlying constant. For structures, sum `maxBitwidth` of constituent fields (honoring arrays with `maxValue` element counts).

Validate:
- Every parameterizable type has `maxBitwidth > 0`.
- Every parameterizable constant has `maxValue > 0`.
- The currently-resolved value does not exceed the declared max — emit a **hard generator error** (not a warning) if it does.

Propagation may require iterative fixed-point convergence for chains (e.g., a constant derived via `eval` from a parameterizable constant, used as the `width` of a type, used as the `arraySize` of a struct field). A topological sort based on the dependency graph is preferred if feasible; otherwise iterate until stable.

#### Step 4: Generate Config struct per IP instance

**New generator output.** For each IP instance declared in the consuming project's YAML (see `ipInstances` in `plan-ip-namespaces-and-parameterization.md` Section 4.4), generate a Config struct header:

```cpp
// Generated: debayer_8bpc_config.h
#pragma once
#include <cstdint>

struct debayer_8bpc_config {
    static constexpr uint32_t BITS_PER_PIXEL_COLOR = 8;
    static constexpr uint32_t MAX_PIXEL_VALUE = 255;
    static constexpr uint32_t PIXELS_PER_CLOCK = 4;
    // ... all ipParameters constants with instance-specific values
};
```

Validate at generation time that provided values do not exceed `maxValue`/`maxBitwidth`.

For the IP's own default configuration (used during standalone IP development/testing), generate a default Config struct from the `ipParameters` default values.

#### Step 5: Template parameterizable types

**File:** [builder/base/templates/systemc/includes.py](builder/base/templates/systemc/includes.py)

In `includeTypes` (line 94), when a type is parameterizable:

**Current output:**
```cpp
typedef uint8_t pixel_t; // [8] Per color pixel data
```

**New output:**
```cpp
template<typename Config>
using pixel_t = uint64_t; // Per color pixel data (parameterizable, max bitwidth: 16)
```

- Force `uint64_t` regardless of actual width (per Section 4.6 "Underlying C++ Type Strategy").
- The Config parameter is present for type-graph consistency — `pixel_t<Config>` propagates uniformly through structs even though the underlying type doesn't depend on Config.
- Non-parameterizable types remain plain `typedef` with width-matched platform types.

In `includeConstants` (line 21), **omit** parameterizable constants from the IP's includes header. These constants live only in Config structs. Non-parameterizable constants remain as `const` declarations.

#### Step 6: Template parameterizable structures

**File:** [builder/base/templates/systemc/structures.py](builder/base/templates/systemc/structures.py)

In `oneStruct` (line 249), when a structure is parameterizable:

**6a. Struct declaration becomes a template:**

Current:
```cpp
struct rgb_pixel_t {
    pixel_t r;
    ...
};
```

New:
```cpp
template<typename Config>
struct rgb_pixel_t {
    pixel_t<Config> r;  // parameterizable member type gets <Config>
    ...
};
```

Non-parameterizable member types (e.g., `video_frame_t`) remain unqualified.

**6b. `_bitWidth` uses `Config::` prefix:**

The existing `structBitWidthExpression_cpp` (line 86) already produces symbolic expressions. Modify it so that when a term references a parameterizable constant, it emits `Config::CONSTANT_NAME` instead of bare `CONSTANT_NAME`. When a term references a parameterizable sub-struct, it emits `sub_struct<Config>::_bitWidth` instead of `sub_struct::_bitWidth`.

Current output:
```cpp
static constexpr uint16_t _bitWidth = BITS_PER_PIXEL_COLOR + BITS_PER_PIXEL_COLOR + BITS_PER_PIXEL_COLOR;
```

New output:
```cpp
static constexpr uint16_t _bitWidth = Config::BITS_PER_PIXEL_COLOR + Config::BITS_PER_PIXEL_COLOR
                                      + Config::BITS_PER_PIXEL_COLOR;
```

Similarly, `typeWidthExpression_cpp` (in [includes.py:53](builder/base/templates/systemc/includes.py:53)) must emit `Config::CONSTANT_NAME` when the referenced constant is parameterizable.

**6c. `_packedSt` uses `maxBitwidth`:**

In `convertToType` (line 65), add a parameterizable path: when the struct is parameterizable, use `maxBitwidth` to select the `_packedSt` type. For structs with `maxBitwidth <= 64`, emit `typedef uint64_t _packedSt;`. For `maxBitwidth > 64`, emit `typedef uint64_t _packedSt[N];` where `N = ceil(maxBitwidth / 64)`.

**6d. Non-parameterizable structs remain plain `struct` — no template overhead.**

#### Step 7: Make pack/unpack text-stable with `Config::` expressions

**File:** [builder/base/templates/systemc/structures.py](builder/base/templates/systemc/structures.py)

This is the largest change. When a struct is parameterizable, pack/unpack methods must use `Config::` symbolic expressions instead of resolved numeric literals.

**7a. `fw_pack_oneVar` (line 1040):**

Current shift expression:
```cpp
_ret |= (uint32_t)g << (8 & 31);
```

New (parameterizable):
```cpp
_ret |= (uint64_t)g << (Config::BITS_PER_PIXEL_COLOR & _baseMask);
```

The position value `8` becomes `Config::BITS_PER_PIXEL_COLOR`. The cast becomes `(uint64_t)` (since `_packedSt` is `uint64_t`). The base mask becomes `63` (since `uint64_t` base).

For cumulative positions, use symbolic expressions. When a field's position depends on preceding field widths, emit:
- For fields preceded by non-parameterizable fields: the resolved integer position (text-stable since it doesn't depend on parameters).
- For fields preceded by parameterizable fields: a `Config::` expression or a `_pos` runtime variable with symbolic increments.

**7b. `fw_unpack` (line 867) — same approach:**

Current mask:
```cpp
r = (pixel_t)((_src >> (_pos & 31)) & ((1ULL << 8) - 1));
_pos += 8;
```

New:
```cpp
r = (pixel_t<Config>)((_src >> (_pos & _baseMask)) & ((1ULL << Config::BITS_PER_PIXEL_COLOR) - 1));
_pos += Config::BITS_PER_PIXEL_COLOR;
```

**7c. `get_unpack_mask_str` (line 836):**

Current: takes `needBits` as a resolved integer. For parameterizable fields, it must return a symbolic expression string using `Config::CONSTANT_NAME`.

**7d. `fw_pack_oneNamedStruct` (line 1084):**

Current: uses resolved `data['bitwidth']` for nested struct offsets (e.g., `<< (3 & 63)` for `video_frame_t::_bitWidth`). For parameterizable nested structs, emit `<< (sub_struct<Config>::_bitWidth & _baseMask)`.

**7e. `fw_pack_setup` (line 1026):**

The `_baseMask` value changes for parameterizable structs. Since `_packedSt` is always `uint64_t` for parameterizable structs, `_baseMask` is always `63`. For array-of-`uint64_t` cases, the `pack_bits()` helper path is used.

**7f. Array fields with parameterizable element width:**

Current `pack_bits` call:
```cpp
pack_bits((uint64_t *)&_ret, _pos, pixels[i], 8);
_pos += 8;
```

New:
```cpp
pack_bits((uint64_t *)&_ret, _pos, pixels[i], Config::BITS_PER_PIXEL_COLOR);
_pos += Config::BITS_PER_PIXEL_COLOR;
```

The loop bound is already symbolic (`PIXELS_PER_CLOCK`), and becomes `Config::PIXELS_PER_CLOCK`.

**7g. Compound case:** When both `arraySize` and element `bitwidth` are parameterizable, the compound expression `Config::ELEMENT_WIDTH * Config::ARRAY_SIZE` must be fully symbolic. The `_pos` runtime tracking approach handles this naturally since both the per-element increment and the loop bound are `Config::` constexpr values.

#### Step 8: Move parameterizable struct implementations to headers

**File:** [builder/base/templates/systemc/structures.py](builder/base/templates/systemc/structures.py)

C++ requires template definitions to be visible at the point of instantiation. For parameterizable structs, the `codeMapping` table (line 224) must change the split/inline designation:

Current `codeMapping['model']`:
```python
'fw_pack': 'split',   # declaration in .h, definition in .cpp
'fw_unpack': 'split',
'equal': 'split',
'prtFmt': 'split',
'sc_pack': 'split',
'sc_unpack': 'split',
```

For parameterizable structs, these must become `'inline'` (definition in header). This should be a per-struct decision, not a global mode change. Non-parameterizable structs retain the `split` pattern.

Implementation: the `oneStruct` function (line 249) should check `value.get('isParameterizable', False)` and override the mode's `codeMapping` entries to `'inline'` for that struct. When emitting `.cpp` code, skip parameterizable structs entirely.

Checkpoint status: implemented for the `ip_test` C++20 module path.

The generated structure test harness now follows the same Config-template policy as generated structures when `mode=module`:

#### Step 9: Template parameterizable base class and block class declarations

**File:** Generated base class headers (e.g., `interpolateBase.h`) and block class headers.

When a block uses parameterizable interfaces (i.e., interface structures that are parameterizable), the block's base class and class declaration must become templates:

```cpp
// interpolateBase.h (generated, text-stable):
template<typename Config>
class interpolateBase : public virtual blockPortBase {
public:
    rdy_vld_out< video_rgb_t<Config> > video_rgb_stream;
    rdy_vld_in< bayer_preprocess_stream_t<Config> > bayer_preprocess_stream;
    // non-parameterizable ports remain unqualified
};

// interpolate.h (IP code, text-stable):
template<typename Config>
SC_MODULE(interpolate), public blockBase, public interpolateBase<Config> {
    void processPixel();
    // ...
};
```

The `SC_MODULE` macro expands to `struct name : public sc_module`, so the template declaration is valid C++. However, SystemC macro compatibility (`SC_THREAD`, `SC_METHOD`, `sc_trace`) with template classes requires prototype validation — see Step 14.

#### Step 11: Address-space sizing with worst-case values

**File:** [builder/base/pysrc/processYaml.py](builder/base/pysrc/processYaml.py)

**11a. `calcAddresses` (line 2516):**

At line 2546:
```python
size = roundup_pow2min4((row['width'] + 7) >> 3) * self.qualConstParse(row['wordLinesKey'])
```

When `row['width']` comes from a parameterizable structure, substitute the structure's `maxBitwidth`. When `row['wordLinesKey']` resolves to a parameterizable constant, substitute its `maxValue`.

```python
width = row.get('maxBitwidth', row['width']) if is_parameterizable else row['width']
wordLines = row.get('maxWordLines', self.qualConstParse(row['wordLinesKey'])) if is_parameterizable else self.qualConstParse(row['wordLinesKey'])

```

**11b. Register `bytes` derivation (line 1016):**

```python
ret['registers'][reg]['bytes'] = (self.data['structures'][regInfo['structureKey']]['width'] + 7) >> 3
```

For parameterizable structures, use `maxBitwidth`:
```python
struct_data = self.data['structures'][regInfo['structureKey']]
width = struct_data.get('maxBitwidth', struct_data['width']) if struct_data.get('isParameterizable') else struct_data['width']
ret['registers'][reg]['bytes'] = (width + 7) >> 3
```

Same change needed at line 1509 where `bytes` is derived similarly.

#### Step 13: Runtime `maxBitwidth`/`maxValue` assertions

In generated IP code (both C++ and SV), emit runtime assertions that validate Config values against declared maximums. These serve as a secondary safety net beyond the generation-time checks in Step 3.

**C++ (in generated Config-aware includes):**
```cpp
template<typename Config>
struct _ipParameterValidation {
    static_assert(Config::BITS_PER_PIXEL_COLOR <= 16,
        "BITS_PER_PIXEL_COLOR exceeds maxBitwidth of 16");
    static_assert(Config::PIXELS_PER_CLOCK <= 8,
        "PIXELS_PER_CLOCK exceeds maxValue of 8");
};
```

Use `static_assert` where possible (Config members are `static constexpr`). This catches violations at compile time, not just at generation time.

**SV:** Use `initial` block assertions or `$fatal` in the per-instance package.

#### Step 14: Prototype validation (Phase 0 prerequisite)

Before implementing Steps 5–9, validate SystemC template compatibility:

1. **`SC_MODULE` + `SC_THREAD`/`SC_METHOD`** with `template<typename Config>` — verify function pointer registration works. `SC_CURRENT_USER_MODULE` must capture the correct type.
2. **`sc_trace`** with template struct types — verify the trace infrastructure handles parameterized types.
3. **SystemC signal/channel binding** with template-parameterized port types — verify `rdy_vld<video_rgb_t<Config>>` binds correctly.
4. **`instanceFactory` registration** — the current factory uses string-based block name lookup. Templated blocks need a mechanism for the consuming project to register template instantiations explicitly. This is Phase 3 scope but should be prototyped early.

Prototype with a single block (e.g., `interpolate`) and two Config structs.

### Further considerations

1. **Shared types across IPs and parameterization boundary:** When `isp_types.yaml` is shared between two IPs, its types live in the shared scope. If a type in `isp_types` depends on a parameterizable constant, it becomes `template<typename Config>`. Both IPs must use the same Config type for those shared types — or shared types must be restricted to non-parameterizable definitions only. This boundary must be precisely defined in the YAML schema (likely: `ipParameters` can only appear in the IP's own YAML, not in shared includes).

2. **Cross-config interface prohibition:** Differently-parameterized instances cannot directly communicate via parameterized interface types (e.g., `video_rgb_t<config_a>` is a different type from `video_rgb_t<config_b>`). Communication must use non-parameterized types or explicit adapter blocks. This should be enforced at YAML connection validation time.

3. **`instanceFactory` with templates:** The current factory uses string-based block name lookup. Templated blocks need the consuming project to register template instantiations explicitly (e.g., `factory.register<interpolate<debayer_8bpc_config>>("interpolate_8bpc")`). This is Phase 3 scope.

4. **Transitive propagation depth:** The propagation pass must handle chains (e.g., constant derived via `eval` from a parameterizable constant, used as `width` of a type, used as `arraySize` of a struct field). A topological sort is preferred; iterative fixed-point as fallback.

5. **Array-of-parameterizable-type compound case:** When both `arraySize` and element `bitwidth` are parameterizable, the compound `_bitWidth` expression (`Config::ELEMENT_WIDTH * Config::ARRAY_SIZE`) must be fully symbolic. The `structBitWidthExpression_cpp` function already handles array multiplication with symbolic array sizes — it needs the additional `Config::` prefix for both terms.

6. **`sc_pack`/`sc_unpack` methods:** These use `.range()` accessors with resolved integer bounds (e.g., `.range(7, 0)`). For parameterizable structs, these bounds must become constexpr expressions. Since `sc_bv::range()` takes `int` arguments, constexpr expressions like `Config::BITS_PER_PIXEL_COLOR - 1` should work. However, the cumulative offset tracking in `sc_pack` (line 628) and `sc_unpack` (line 704) uses Python-side integer arithmetic — this must switch to symbolic string-based expression building for parameterizable structs.

7. **SV parameterization strategy:** The SV equivalent of the Config template (per-instance packages, module-level parameters, etc.) is deliberately left open pending EDA tool validation, per the parent plan Section 4.3.

## #116 Review Follow-Up — Item 3: Always-Emit Variant-Named Config (Execution, 2026-07-29)

Hardens Item 3 of `plan-116-review-feedback.md`. **Intent (authoritative):** emit
one distinctly variant-named Config struct for **every** declared variant, so the
emitted config structs map **1:1** onto the declared variant set — including a
variant whose resolved values equal the block default. Today such a variant is
deduped onto the shared context default (`<contextStem>DefaultConfig`), so no
variant-named struct is emitted and consumers silently fall back to the default
name. Readers cannot tell from the generated code which variants exist.

### Dedup site (where the fold happens)

All folding lives in the projectOpen view helper
`processYaml.py::_buildVariantConfigDescriptors` (`pysrc/processYaml.py:1600-1764`).
Two mechanisms suppress a per-variant struct:

- **Default-fold** — the shared context default is seeded as the canonical struct
  for the default value signature (`processYaml.py:1717-1722`, `_DEFAULT_SIGNATURE`
  sentinel). A same-project variant whose signature matches takes the
  `elif canonical is _DEFAULT_SIGNATURE:` branch (`processYaml.py:1746-1749`),
  which sets `useDefault=True`, `duplicateOf={'kind':'default'}`,
  `emitVariant=variant`. This is exactly the default-equal case Item 3 targets.
- **Sibling-fold** — a later variant byte-identical to an earlier sibling folds
  onto it (`processYaml.py:1739-1743, 1750-1753`), setting
  `duplicateOf={'kind':'variant', ...}`, `emitVariant=canonical`.

The template consumes these markers but does not compute them. In
`templates/systemc/config.py::includeConfig` (`config.py:143-146`) a descriptor
with `duplicateOf is not None` is skipped, so no struct is emitted for a folded
variant. Per-instance type selection reads the same markers via
`intf_gen_utils.py::cpp_descriptor_config_name` (`intf_gen_utils.py:423-432`):
when `useDefault` is true it returns `defaultConfig`, which is why a default-equal
variant's instances are typed on `<contextStem>DefaultConfig`.

### Naming scheme (so item names are concrete)

Struct names are spelled only in the template layer by
`intf_gen_utils.py::cpp_variant_config_name` (`intf_gen_utils.py:407-421`) from the
descriptor's neutral `(project, block, variant, isForeign)` components:

- Named variant, same-project: `<block><Variant>Config`, where `<Variant>` is the
  variant label with its first character upper-cased (e.g. block `blockF` +
  variant `variant0` → `blockFVariant0Config`; `dut` + `dutV0` → `dutDutV0Config`).
- Anonymous variant (`variant == ''`): `<block>Config`.
- Foreign (assembler-declared) variant: owner-qualified
  `<project>_<block><Variant>Config`.

The shared context default keeps its separate spelling
`<contextStem>DefaultConfig` (`config.py:126`).

### The change (view vs template split)

Per `builder-base-development`, the ownership decision (which variants get their
own struct) is a projectOpen view concern, not a template concern. The template
stays a pure select/iterate/format layer.

- **View change (owns the decision) —
  `_buildVariantConfigDescriptors`:** stop folding declared variants. Every
  declared variant becomes canonical: `duplicateOf=None`, `useDefault=False`,
  `emitVariant=variant`. Concretely, drop the `_DEFAULT_SIGNATURE` seed
  (`processYaml.py:1717-1722`) and the `canonical_by_signature` signature dedup
  (`processYaml.py:1739-1753`) so the `canonical is None` path is taken for every
  variant. The descriptor's `values` are unchanged, so the emitted struct is an
  **independent copy** whose content equals the default when the variant is
  default-equal.
- **Independent copy vs alias (decision):** emit an **independent copy** — a
  standalone `struct <block><Variant>Config { ... }` with the variant's own
  resolved members. This is the simplest option that satisfies "distinctly named,
  1:1": the template already builds each canonical struct body from
  `desc['values']`, so making the descriptor canonical yields the copy with no new
  emission code and no C++ alias/inheritance/`using` machinery. A default-equal
  copy is byte-identical in content to `<contextStem>DefaultConfig` but is a
  distinct C++ type named after the variant.
- **Template change (none of substance) —
  `config.py::includeConfig`:** because no descriptor is now a duplicate, the
  existing loop emits one struct per declared variant with no logic change. The
  existing `seen_struct_names` redefinition guard (`config.py:142,153-155`) is
  **retained**: it is the one legitimate skip, covering a variant literally named
  `default` whose spelled name collides with `<contextStem>DefaultConfig` (see the
  debayer case below). Per-instance typing via `cpp_descriptor_config_name` now
  returns the variant name for these instances automatically, because
  `useDefault` is false; the `not desc['values']` branch is unaffected.

### Debayer reference case

`model/debayerVariantConfig.h` today shows only `debayerDefaultConfig` because
`yaml/debayer.yaml` declares a single variant literally named `default` whose
values equal the ipParameters defaults (`BITS_PER_PIXEL_COLOR=8`,
`PIXELS_PER_CLOCK=4`, `HORIZONTAL_SIZE=3840`, `VERTICAL_SIZE=2160`). For this
block the variant-named spelling is `debayer` + `Default` + `Config` =
`debayerDefaultConfig`, which coincides with `<contextStem>DefaultConfig`
(context stem `debayer` == block `debayer`). So debayer gains **no new struct
name** and **no consumer churn**; the `seen_struct_names` guard keeps the single
`debayerDefaultConfig` struct and the 1:1 mapping is satisfied by that struct
serving as the `default` variant's config. This coincidence is block-specific
(block name == context stem) and does not generalize.

## Update 2026-08-04 — review items 3 and 8 LANDED

This plan is the owner for two #116 review outcomes. Both are closed.

### Item 3 — one configuration structure per variant

Previously a variant whose resolved values equalled the default, or equalled a
sibling variant, received no distinct structure, so consumers silently fell back
to the default-named structure and a reader could not tell from the generated
code which variants existed. **Both folds are removed** in
`_buildVariantConfigDescriptors` (`pysrc/processYaml.py`, comments at `:1678` and
`:1778-1779`): the default fold and the sibling value-signature fold. Every
declared variant is now an independent canonical descriptor.

The emitted shape is **N+1**: a block with `ipParameters` always emits
`<stem>DefaultConfig` from the ipParameters' declared values — this is the
baseline, never a fold, and never suppressed — plus exactly one
`<block><Variant>Config` per declared variant. Confirmed in
`examples/xif/model/xifVariantConfig.h`, which emits `xifDefaultConfig` alongside
`dutDutV0Config`, `sinkSinkV0Config`, and `srcSrcV0Config`. A block with no
`ipParameters` has no parameters and so raises no variant question at all. This
composes with item 2's completeness rule: because every variant binds every
parameter, each variant's configuration is fully explicit and independent.

### Item 8 — `inheritContainerParam`

Item 3's strict one-to-one per-block configuration exposed a real limitation,
found by dogfooding on the debayer product: two sibling contained blocks sharing
one configuration context each received a distinctly *block*-named structure with
byte-identical fields but distinct C++ types, so a shared
configuration-parameterized channel payload between them could not bind — no
single `Config` satisfied both the producer and the consumer port.

Resolution is an explicit per-**instance** flag. A contained-block instance may
declare `inheritContainerParam: true` **in place of** its `variant:` selector and
is then typed with the container block's active configuration, transitively: if
the container is itself instantiated as variant `V1`, the child gets
`<container>V1Config`. The child block keeps its own `params:` and still emits its
own `DefaultConfig` for standalone use, so item 3 is untouched — only the
contained instance's configuration *selection* changes.

The mechanism is the key simplification: a contained child renders inside the
container's templated class scope, so inheritance reduces to spelling the
container's own template symbol `Config` for that instance
(`pysrc/intf_gen_utils.py:440`), and C++ template instantiation resolves the
concrete struct, including the transitive variant case, at the container's own
instantiation site. No configuration value is plumbed.

Five preconditions are enforced at database time in
`calcBlockConfigInfo::validate_inherit_container_params`
(`pysrc/processYaml.py:4570-4617`), relocated there from an initial
`postParseChecks` home so they run once off that pass's prebuilt maps with no
parse-timing or SQL concerns: the child's params must be a by-name subset of the
container's; `variant:` and `inheritContainerParam:` are mutually exclusive; the
container must be parameterized; the child must have params; and the container and
child must share an owning project. The same-project restriction is what preserves
item 1's owner-qualified identity. The subset check is load-bearing for the
untouched SystemVerilog parameter-forwarding path, which is why it must run in
`projectCreate`. Coverage: `unittest/test_inherit_container_param.py`.

Two HDL-wrapper follow-ons were surfaced by the debayer acceptance and landed with
it: a `hasVl` leaf instantiated *only* via `inheritContainerParam` has an empty
*instantiated*-variant view, which broke wrappers keyed off it. Both now source
from the block's DECLARED variants and params instead — `param_names` reads the
declared `params`, and a new `projectOpen` `declaredVariants` view field feeds the
per-variant trampoline dispatch. The second of those fixed a *silent* misrender:
a declared-but-uninstantiated variant had fallen through to the
non-parameterizable render path and emitted a broken parameterless `.sv`.

**Deferred:** the cross-project negative fixture for precondition (e), because it
needs a composed multi-project fixture rather than a single-file unit fixture. The
precondition itself is implemented and enforced.
